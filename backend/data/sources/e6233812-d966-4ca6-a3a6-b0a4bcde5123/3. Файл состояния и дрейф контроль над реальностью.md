

Код в репозитории задаёт желаемое состояние инфраструктуры, а в облаке в каждый момент существует фактическое. Если между ними нет надёжной связи и регулярной сверки, Terraform исходит из одних вводных, а в облаке уже существуют другие сущности. На практике это приводит к проблемам при `apply`, дубликатам ресурсов, нарушением зависимостей и риском повредить продакшн.

Связующее звено между манифестами и реальными ID объектов в облаке — **файл состояния (state)**. В этом уроке вы настроите **remote state** (хранение state в Object Storage) и разберётесь, зачем это нужно в командной работе и CI, научитесь находить и интерпретировать **дрейф (drift)** — расхождение между кодом и фактом в облаке, а также выполните импорт уже существующих ресурсов под управление Terraform без их пересоздания.


## Зачем нужен файл состояния?

В прошлом уроке мы говорили об идемпотентности Terraform — о том, что он не пересоздаёт сущности в облаке без необходимости, а только сверяет код с реальностью и вносит точечные изменения. Возникает логичный вопрос: откуда Terraform вообще знает, что уже существует в облаке?

Теоретически он мог бы каждый раз ходить в API облака и собирать статусы инстансов на лету, но на практике это медленно и неудобно. Поэтому Terraform хранит состояние в отдельном файле — `terraform.tfstate`. Это, пожалуй, самый важный компонент во всей работе с инструментом.

Файл состояния решает сразу несколько задач.

**Связка кода с реальными объектами.** В коде (`.tf`) вы пишете абстрактное имя (например, `resource "aws_instance" "my_server"`), но в облаке этот сервер получает уникальный ID (например, `i-0abc12345`). Terraform записывает эту связку в state, чтобы при следующем запуске понимать: `my_server` из кода — это конкретный инстанс в облаке.

**Хранение зависимостей.** Не все данные можно получить напрямую из облака. State хранит зависимости между ресурсами. Например, он помнит, что база данных должна создаваться строго после настройки сети — это помогает строить правильный граф ресурсов при запуске кода.

**Кеширование.** При большой инфраструктуре опрашивать API облачного провайдера по каждому ресурсу на каждый `plan` — долго. State работает как кеш и ускоряет работу.

**Блокировка при совместной работе.** Когда над проектом работают несколько инженеров или параллельно запускаются CI-пайплайны, state должен блокироваться. Если один человек выполняет `terraform apply`, файл блокируется — второй не сможет вносить изменения одновременно. Это предотвращает состояние гонки и порчу инфраструктуры. Механизм блокировки обеспечивается [бэкендом Terraform](https://developer.hashicorp.com/terraform/language/backend), о котором мы подробнее поговорим ниже.

Если удалить `.tfstate`, Terraform потеряет всю инфраструктуру из виду. При следующем `plan` он решит, что ничего не создано, и попытается создать дубликаты всех ресурсов. Придётся либо удалять всё в облаке вручную, либо использовать `terraform import`, чтобы заново показать Terraform каждый существующий ресурс (подробнее об этом вы можете почитать [здесь](https://developer.hashicorp.com/terraform/language/import)).

Важно!

Файл состояния часто содержит конфиденциальные данные (пароли, ключи доступа) в открытом виде (JSON). Поэтому его никогда не стоит хранить в публичном Git-репозитории без шифрования.

## Как выглядит state на практике

Разберём, как ведёт себя `terraform.tfstate` локально — поведение будет аналогичным и при удалённом хранении с настроенным бэкендом.

После успешного `terraform apply` с манифестом нашего `main.tf` в рабочей директории появляются два файла: `terraform.tfstate` и `terraform.tfstate.backup`. Оба относятся к одному и тому же состоянию, но выполняют разные роли.

**`terraform.tfstate`** — основной файл состояния. Terraform хранит в нём связь между ресурсами в коде и объектами в облаке, их атрибуты и служебные данные. При `terraform plan` он сопоставляет код (`.tf`) с тем, что записано в state, и строит план: что создать, что изменить, что удалить. Без актуального state Terraform не знает, какие сущности уже «его».

**Два важных правила:** файл нельзя править вручную — риск рассинхронизации с реальной инфраструктурой слишком высок. Кроме того, в state нередко попадают чувствительные данные: пароли, ключи, IP-адреса. Храните его там, где ограничен доступ, и не коммитьте в открытый репозиторий без шифрования. Чтобы минимизировать утечки секретов в выводах и логах, обычно используют в связке:

1. Атрибут `sensitive = true` у выводов и полей, которые не должны светиться в консоли.
2. Внешние хранилища секретов (Vault, менеджеры секретов облака и т. п.), чтобы получать секреты из них.
3. Переменные окружения для значений, которые нельзя держать в файлах репозитория.

Подробнее об этом мы поговорим в следующих уроках.

**`terraform.tfstate.backup`** — резервная копия предыдущего состояния. При `apply` или `destroy` Terraform сначала сохраняет текущую версию в `.backup`, затем записывает новое состояние в `terraform.tfstate`. Это позволяет откатиться или сравнить версии, если что-то пошло не так.

Чтобы сравнить файлы, обратимся к примеру из прошлого урока, когда вы меняли значение `nat` у машины. Сделать это можно c помощью утилиты `diff`:

```
diff terraform.tfstate terraform.tfstate.backup 
```

Станет видно, что изменилось между двумя применениями — среди прочего могут фигурировать поля `serial`, `nat`, `nat_ip_address`, `nat_ip_version`. Посмотрите на них внимательно, затем поменяйте ещё какой-нибудь параметр ВМ на своё усмотрение и проанализируйте, что изменится в `terraform plan`, `terraform apply` и `diff` между стейтами.


## Работа с состоянием Terraform

У CLI Terraform есть опции для ручного управления state.

Например, эта команда выведет список текущих ресурсов, описанных в state:

```
terraform state list 
```

Если виртуальная машина задеплоена, в выводе появится `yandex_compute_instance.vm-1`. Атрибуты конкретного ресурса можно посмотреть отдельно:

```
terraform state show yandex_compute_instance.vm-1 
```

В выводе мы получим все параметры ВМ.

Подробнее с работой CLI можно ознакомиться, вызвав справку:

```
terraform state --help 
```

## Удаление из файла состояния Terraform

`terraform state rm` удаляет запись о ресурсе из state, не обращаясь к API провайдера. Сам объект в облаке (ВМ, диск, сеть) при этом никуда не исчезает: Terraform просто перестаёт считать его частью управляемой инфраструктуры. Это не то же самое, что `terraform destroy` или `-target`, которые инициирует реальное удаление через провайдера.

Зачем это может понадобиться? Например, если в state попал лишний или ошибочно привязанный ресурс и нужно вывести его из-под управления Terraform, не трогая облако. Иногда `state rm` используют как шаг при сложном рефакторинге вместе с [`terraform state mv`](https://developer.hashicorp.com/terraform/cli/commands/state/rm) — но это уже архитектурная задача, которая возникает при переходе от вручную поднятой инфраструктуры к централизованному IaC. Примерно то, о чём мы говорили в контексте серверов-снежинок, серверов-фениксов и immutable infrastructure.

Синтаксис: один или несколько адресов, как в `terraform state list` (можно удалить сразу несколько ресурсов):

```
terraform state rm yandex_compute_instance.vm-1 
```

## Импорт в файл состояния Terraform

Допустим, вы выполняете `terraform plan` и видите, что данные в state не соответствуют реальному состоянию облака. Скорее всего, инфраструктура поднималась вручную, в обход IaC. Это частая ситуация — в реальности строго следовать парадигме «инфраструктура как код» удаётся не всегда.

Чтобы передать такой ресурс под управление Terraform, используют `terraform import`. Например, для ВМ, созданной вручную:

```
terraform import yandex_compute_instance.<Имя ресурса ВМ> <ID машины> 
```

`terraform import` — это вторая часть того архитектурного вызова, который мы уже затрагивали при разговоре про `state mv`. Переход от ручной инфраструктуры к централизованному IaC решается в два шага: сначала импортируют все ресурсы, чтобы положить их описание в репозиторий, затем делят этот репозиторий на отдельные сущности — сеть, ноды кластера БД и т. д. Для второго шага нужен `state mv`. Дальше начинаются вопросы про модули, монорепу, согласование между командами — но это уже отдельная история, оставим её архитекторам.

После того как инфраструктура переведена в код Terraform, любое ручное изменение через GUI облака снова создаёт дрейф конфигурации. Бороться с ним можно несколькими способами:

1. **Регулярные проверки через `terraform plan`** — в том числе джоба в CI, которая по расписанию проверяет инфраструктуру и алертит при неожиданных расхождениях.
2. **Запрет ручных изменений** — подход GitOps, когда все правки вносятся только через Git, а изменения в консоли облака запрещены.
3. **Immutable infrastructure** — ресурсы не изменяются, а пересоздаются.
4. **Блокировка state** — `state locking` предотвращает одновременные правки.
5. **Интеграция со сторонними сервисами** — например, [Hashicorp Sentinel](https://www.hashicorp.com/en/sentinel) позволяет проверять код на соответствие политикам до применения изменений.


## Хранение состояния на удалённом ресурсе

Локальное хранение state рядом с манифестами создаёт несколько серьёзных проблем:

1. **Потеря файлов**. Несмотря на `terraform.tfstate.backup`, state легко потерять, просто удалив файлы.
2. **Безопасность**. Файлы состояния содержат конфиденциальные данные, поэтому их нельзя оставлять в открытом доступе вместе с основными манифестами.
3. **Совместная работа.** Когда над инфраструктурным кодом работают несколько человек, у каждого локально находится своя версия `terraform.tfstate` — из-за этого Terraform не может определить актуальное состояние инфраструктуры.
4. **Нет истории изменений.** Локально хранится только одна предыдущая версия — глубокой истории нет.

Решение — хранить state в удалённых ресурсах. Terraform предоставляет для этого множество бэкендов. [По умолчанию](https://developer.hashicorp.com/terraform/language/backend/local) используется бэкенд `local`, но есть и другие (например: S3, `pg`, `consul`, `http`). В рамках одного рабочего окружения можно использовать только один бэкенд.

Популярный вариант — **S3-бакет (Simple Storage Service)**, объектное хранилище для файлов. Здесь данные лежат в специальных контейнерах (бакетах). Взаимодействие с S3 происходит по `http`, а для доступа к бакету используется уникальный набор ключей. У Яндекс Облака также есть [поддержка S3](https://yandex.cloud/ru/docs/storage/?utm_referrer=about%3Ablank).

В облаках часто создают отдельные [сервис-аккаунты](https://yandex.cloud/ru/docs/iam/concepts/users/service-accounts) для доступа к конкретным ресурсам — это упрощает управление ими. В Практикуме для работы с S3 уже заранее сделан сервис-аккаунт с нужными правами.

## Практическое задание 3. Настройка хранения state в S3

Для начала нам нужно создать бакет.

Это можно сделать с помощью `yc` или вручную в облачной консоли. Мы пойдём по второму пути, поэтому:

1. Залогиньтесь в [облачную консоль](https://console.yandex.cloud/) под федеративным аккаунтом. Выберите фолдер своей когорты.
2. Перейдите в раздел **Object storage**, выберите **Создать бакет** в правом верхнем углу.

![](https://pictures.s3.yandex.net/resources/3-3-1_1766175291.png)

3. Укажите уникальное имя бакета `<student id>-terraform`, остальные настройки оставьте без изменений. Далее — **Создать бакет**.

Чтобы сервис-аккаунт смог получить доступ к бакету, ему необходим [статический ключ доступа](https://yandex.cloud/ru/docs/iam/concepts/authorization/access-key). Это **не то же самое, что IAM-токен**. Подробнее про способы авторизации в облаке вы можете почитать [здесь](https://yandex.cloud/ru/docs/iam/concepts/authorization/).

Теперь выпишем ключ. Для этого:

1. Найдите сервис-аккаунт `general-sa` с правами `editor` в разделе **Identity and Access Management**.
2. Выберите справа вверху **Создать новый ключ**, далее — **Создать статический ключ доступа**.

![](https://pictures.s3.yandex.net/resources/3-3-2_1766175298.png)

3. Заполните описание, указав свой **student ID**.
4. Сохраните себе локально идентификатор ключа и сам ключ.

С помощью полученных ключей вы сможете обращаться к S3-бакету от имени сервис-аккаунта. Осталось настроить миграцию состояния из локального хранилища в S3.

Укажите конфигурацию используемого бэкенда. Дополните файл `main.tf`:

```
terraform {
  required_providers {
    yandex = {
      source = "yandex-cloud/yandex"
    }
  }

  backend "s3" {
    endpoint = "https://storage.yandexcloud.net"
    bucket = "<имя бакета>"
    region = "ru-central1"
    key    = "state/terraform.tfstate"

    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requesting_account_id  = true
    skip_s3_checksum            = true 
  }
} 
```

После этого заполните переменные окружения полученными ключами:

```
export ACCESS_KEY="<идентификатор_ключа>"
export SECRET_KEY="<секретный_ключ>" 
```

Инициализируйте Terraform командой:

```
terraform init -backend-config="access_key=$ACCESS_KEY" -backend-config="secret_key=$SECRET_KEY" 
```

Terraform предложит провести миграцию. Выберите `yes` и убедись, что в облачной консоли в бакете появился файл состояния.

В одном бакете можно хранить множество файлов состояния разных проектов, если указать разные пути в параметре `key`.

Обратите внимание, что [access key](https://developer.hashicorp.com/terraform/language/backend/s3#access_key) и [secret key](https://developer.hashicorp.com/terraform/language/backend/s3#secret_key) можно явно прописать в блоке `backend "s3"`, но это плохая практика — секреты не должны лежать в репозитории в открытом виде. Удобнее передавать их через переменные окружения и `-backend-config`, как мы сделали выше с `ACCESS_KEY` и `SECRET_KEY`.

Важно!

Бэкенд называется `s3` не потому, что state обязан жить в AWS, а потому что используется S3‑совместимый API (им как раз является Yandex Object Storage). Внутри этот бэкенд умеет подхватывать привычные для AWS SDK имена переменных — `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Это не «ключи Amazon», а просто **устоявшиеся имена** в Terraform для пары идентификатор/секрет при доступе к любому S3‑совместимому хранилищу — библиотека внутри провайдера работает так, как будто перед ней обычный S3.

Не стоит путать их с `YC_TOKEN` или `YC_SERVICE_ACCOUNT_KEY_FILE` — переменными Yandex Cloud (или других provider-wide переменных). Если задать их в окружении, часто можно не дублировать ключи в `-backend-config` (см. [документацию бэкенда](https://developer.hashicorp.com/terraform/language/backend/s3)). В уроке мы явно прокинули ключи в `terraform init`, чтобы было понятно, откуда они берутся.

### Если `terraform destroy` (или `plan` / `apply`) падает с ошибкой после переноса state в S3

Поведение `terraform destroy` **не меняется** из‑за remote backend: команда по-прежнему удаляет ресурсы у провайдера и обновляет state в бакете. Чаще всего ошибки после миграции связаны не с `destroy`, а с **доступом к бакету** или с **окружением**, в котором вы запускаете Terraform.

**Что проверить:**

1. **Те же учётные данные, что и при `terraform init`.** Ключи статического доступа к Object Storage действуют только в той сессии терминала, где вы выполнили `export`. В новом окне или после перезагрузки переменные пусты — Terraform не сможет прочитать или записать `terraform.tfstate` в бакете. Либо задайте снова `ACCESS_KEY`/`SECRET_KEY` и при необходимости повторите `terraform init` с теми же `-backend-config`, что в уроке; либо экспортируйте `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` (это [совместимые с бэкендом `s3` имена](https://developer.hashicorp.com/terraform/language/backend/s3) для пары идентификатор/секрет к S3‑совместимому хранилищу), затем снова `terraform init` (если бэкенд ещё не инициализирован в этой сессии).
2. **Вы в каталоге с тем же `main.tf`, где настроен блок `backend "s3"`**, и выполняли `terraform init` именно здесь после добавления бэкенда. Иначе Terraform может искать state локально или в другом бакете.
3. **Права сервисного аккаунта на бакет.** Для `destroy` Terraform должен **записать** обновлённый state в объект (`put`/`delete` объекта state). Если в ошибке фигурируют `403`, `AccessDenied`, `Forbidden` — проверьте, что у ключа есть права на нужный бакет и префикс `key` (в уроке — `state/terraform.tfstate`), а политика бакета не запрещает операции от имени этого сервисного аккаунта.
4. **Текст ошибки.** Сообщения вроде «No valid credential sources found», «failed to get object», «error acquiring the state lock» указывают на ключи, сеть или блокировку state, а не на то, что `destroy` «не поддерживается» с S3.

Когда проблема с доступом к бакету устранена, выполните `terraform plan` — он должен отработать без ошибок бэкенда; затем снова `terraform destroy`.

Мы настроили хранение файла состояния в удалённом ресурсе. Теперь каждому, кто работает с манифестами, требуется аутентификация по ключам для доступа к актуальному состоянию.
