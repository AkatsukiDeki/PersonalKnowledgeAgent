- ## Зачем Git нужен DevOps-команде?
- Когда мы говорим о DevOps, мы в первую очередь говорим о культуре: о сотрудничестве между разработкой и эксплуатацией, об автоматизации процессов, о способности компании быстро реагировать на изменения. Но культура — вещь тонкая. Её нужно строить на основе поддерживающих практик и инструментов.
- Одним из таких инструментов является Git — распределённая система контроля версий, без которой трудно представить современную DevOps-команду. Это инфраструктура для совместной работы, инструмент коммуникации с опорой на историю.
- ### Git против антипаттернов
- В предыдущем уроке мы говорили об антипаттернах в инженерной культуре: silo-мышление, blame-культура, отсутствие прозрачности, плохая передача знаний и коммуникация. Все они в той или иной форме сводятся к одной проблеме — отсутствию общей картины и общей ответственности.
- Git борется с этим на практике:
    - Все работают в одном пространстве изменений. Нет отдельных версий «у Пети» и «у Маши». Есть единая история для всех.
    - Изменения сохраняются в виде осмысленных коммитов, а не исчезают в Slack или устной договорённости.
    - История изменений доступна и проверяема: кто, когда и зачем поменял конкретный кусок кода.
    - Коммиты становятся документацией — не по принуждению, а естественным образом.
    - «Героизм» сводится к минимуму, процессы становятся более устойчивыми: когда кто-то уходит в отпуск или увольняется, команда не теряет знания.
- Короче говоря, Git — это инструмент распределённой ответственности, который делает из разработки и сопровождения системный процесс.
- ### Принцип Codebase и Git
- В [12-факторной методологии](https://12factor.net/ru/), которая лежит в основе многих современных подходов к DevOps, есть чёткий принцип: «одна кодовая база на приложение». Это не значит, что всё должно быть в одном репозитории, — должен быть один источник правды, с которым работают все члены команды.
- Git реализует этот принцип идеально: сам репозиторий и есть codebase. Даже если проект состоит из нескольких сервисов или репозиториев, каждый из них остаётся самостоятельной codebase с единой, прозрачной историей изменений.
- Благодаря Git вы можете:
    - гарантировать, что CI-процессы всегда работают с определённым состоянием кода;
    - понимать, когда и почему появилась каждая строка конфигурации;
    - видеть, какие изменения были частью конкретной фичи, релиза или хотфикса.
- ### Git и CALMS
- Если вспомнить модель CALMS (Culture, Automation, Lean, Measurement, Sharing), то Git затрагивает все её компоненты:
    - Culture — культура совместной работы и прозрачности.
    - Automation — Git является точкой входа для CI/CD, инфраструктуры как кода, автоматизации.
    - Lean — история коммитов помогает дробить изменения, работать с минимальными инкрементами.
    - Measurement — из Git легко извлекаются метрики эффективности DevOps-изменений (частота деплоев, время восстановления после инцидента и т. д.).
    - Sharing — ветки, пулл-реквесты, ревью — всё это обмен знаниями.
- Да, Git — незаменимый компонент!

- ### Почему Git стал стандартом
- Раньше многие команды использовали централизованные системы контроля версий (например, SVN или Perforce). В них была одна центральная точка, и каждый разработчик «просил» у сервера нужные версии файлов. Это выливалось в зависимость от сервера, сложности с офлайн-работой, жёсткие блокировки и трудности с параллельной работой.
- Git предложил другую модель — распределённую. У каждого разработчика есть полная история, работать можно офлайн, есть продвинутое ветвление и возможность слияния веток. Это сделало Git идеальным для открытых проектов (например, в GitHub), а затем — и для корпоративной разработки.
- Но главное, Git идеально ложится в идеологию DevOps:
    - автономия команд,
    - непрерывность интеграции и доставки,
    - поддержка инфраструктуры как кода и GitOps-подходов,
    - инструмент для экспериментов с безопасным откатом.

- ## Как работает Git
- Git может настораживать новичков: ты что-то пишешь в консоли, потом вводишь `git push`, и вдруг код оказывается где-то на сервере. А иногда наоборот — всё исчезает, или появляется странный конфликт, и никто не понимает, что происходит.
- Но если разобраться, как Git устроен изнутри, страхи и путаница исчезнут.
- Представьте, что вы работаете над книгой — вымышленной историей, которую сами же и придумали. Вы пишете её по главам, иногда возвращаетесь к предыдущим страницам, что-то переписывая или уточняя. Чтобы не потерять ни одной идеи, сканируете каждую версию главы и сохраняете её в архив, при этом отмечая, когда и зачем вносились изменения. Примерно так Git и работает, при этом он ещё фиксирует автора изменений.
- Теперь представьте, что над этой книгой работают сразу несколько авторов. Каждый пишет в своей копии, добавляет главы, исправляет сцены, предлагает новые развязки. Время от времени все авторы синхронизируются и отправляют свои изменения в общий репозиторий.
- Иногда случается, что два автора одновременно редактируют одну и ту же главу. При объединении возникает конфликт — какую версию оставить? Это как если бы в двух экземплярах книги одна и та же сцена была написана по-разному, и редактору нужно выбрать, какую из версий выбрать в качестве финальной, и сделать это вручную.
- Так устроен Git: каждый работает автономно, как независимый автор, а репозиторий — это общий редакторский архив, где собирается окончательный вариант книги. Благодаря этой архитектуре можно одновременно работать над разными частями проекта, не мешая друг другу, и при этом всегда сохранять целостность итоговой версии.
- 
- ### Распределённая модель: у каждого — вся история
- Первая важная особенность Git — его распределённость. То есть у каждого разработчика на локальной машине хранится вся история изменений — не только текущие файлы, но и все коммиты и ветки, даже теги. В отличие от SVN или других централизованных систем, вам не нужно обращаться к серверу, чтобы просмотреть историю или сделать коммит. Вы можете работать офлайн, коммитить локально, делать ветки и даже экспериментировать со слияниями — всё без подключения к интернету.
- Почему это важно:
    - работа становится быстрой и надёжной: никакой зависимости от центрального сервера;
    - можно создавать локальные эксперименты без риска сломать что-то у всех;
    - Git идеально подходит для CI/CD, где каждый пайплайн может клонировать код и иметь полный контекст.
- Итак, Git — это распределённая система, в которой каждый работает с локальной копией репозитория, а не напрямую с сервером. Изменения можно вносить офлайн и синхронизировать с сервером, когда нужно, — благодаря этому Git остаётся гибким, надёжным и устойчивым к сбоям.
- ### Локальное хранилище
- Когда вы клонируете репозиторий с помощью команды `git clone`, Git создаёт у вас на машине полную копию репозитория, то есть все файлы проекта, всю историю изменений (все коммиты, ветки и теги), а также собственный `.git`-каталог (это и есть база данных Git).
- Вы можете коммитить, смотреть историю, откатываться и экспериментировать локально, даже без доступа к интернету.
- ### Удалённое хранилище
- Обычно проект также хранится на удалённом сервере (например, на GitLab, GitHub или Bitbucket). Это нужно, чтобы другие члены команды могли видеть ваши изменения и делиться своими.
- Когда вы внесли изменения в код в локальном хранилище, их нужно отправить на сервер — это делается командой `git push`. А когда вы делаете `git pull` или `git fetch` — вы получаете изменения от других.
- Удалённое хранилище — это точка синхронизации между участниками проекта, но не центр управления. Вся основная работа идёт у вас локально.
- ### Модель трёх состояний: рабочая директория, индекс, репозиторий
- Вторая важная особенность Git — он отслеживает состояние файлов на трёх уровнях:
    1. Working directory (рабочая директория) — здесь вы редактируете файлы, создаёте новые, удаляете — это просто обычная файловая система.
    2. Staging area (или Index) — сюда вы «готовите» изменения для будущего коммита с помощью `git add`.
    3. Repository (локальный репозиторий) — это база данных Git, где лежат все сделанные коммиты. Вы пополняете её с помощью `git commit`.
- При этом файлы могут находиться в трёх состояниях:
    1. `modified` — файл был изменён, но Git пока о нём «не знает». Эти изменения находятся в рабочей директории.
    2. `staged` — файл был добавлен в индекс, то есть Git готов включить его в следующий снимок (коммит).
    3. `committed` — файл уже стал частью истории изменений. Его состояние зафиксировано в локальном репозитории.
- Пример:
- 
- .
    ```
    ```
# Вы меняете файл index.js
nano index.js

# Git показывает, что файл изменён
git status

#On branch main
#Your branch is ahead of 'origin/main' by 2 commits.
#  (use "git push" to publish your local commits)
#
#Changes not staged for commit:
#  (use "git add <file>..." to update what will be committed)
#  (use "git restore <file>..." to discard changes in working directory)
#    modified:   index.js
#
#no changes added to commit (use "git add" and/or "git commit -a")

# Вы добавляете его в индекс
git add index.js

# Коммитите
git commit -m "feat: добавлен вывод приветствия"
```
    ```
- Вот простая аналогия: сначала вы пишете черновик (working directory), затем переписываете его начисто (staging), и наконец складываете в архив (commit).

- ### Коммит: снимок состояния, а не просто дельта изменений
- Важно понимать: Git не хранит разницу между версиями, как это делает, например, SVN. Git хранит снимки (snapshots) — полное состояние проекта в момент коммита. Если файл не менялся — он просто ссылается на уже существующую версию.
- Каждый коммит имеет уникальный SHA-1 хеш — последовательность из 40 символов, которая создаётся на основе содержимого, метаданных и родительских коммитов. Именно поэтому история Git почти неизменяема: если изменить даже один байт — хеш изменится, и Git это заметит.
- ### HEAD, ветки и хранилище объектов
- По своей сути Git — это база данных, которая хранит определённые объекты (коммиты, деревья, файлы). Но чтобы понимать, где мы находимся и что означает имя `main`, существует система ссылок — `refs`.
- Удобно представить коммиты как коробки на складе: у каждой есть уникальный автоматически сгенерённый хеш (например, `a1b2c3d`), который сложно запомнить. Чтобы облегчить пользователям жизнь, Git использует указатели с человеческими именами — ветки и теги.
- 
- #### Ветки — подвижные указатели на коммиты
- Ветка — это просто файл в папке `.git/refs/heads/`, внутри которого лежит хеш коммита. Когда вы делаете новый коммит на ветке `main`, Git автоматически обновляет этот файл — теперь он указывает на новый коммит.
- 
- .
    ```
    ```
# Посмотрим, на какой коммит указывает ветка main
$ cat .git/refs/heads/main
85b07803043b8a8f7a91ec8414cbdfdbfac09813
```
    ```
- Эти указатели двигаются автоматически: каждый новый коммит перемещает указатель ветки вперёд, перезаписывая содержимое соответствующего файла.
- 
- 
- ### HEAD — указатель на текущее место
- `HEAD` — это специальная ссылка, которая показывает, где вы находитесь прямо сейчас. Обычно `HEAD` указывает на какую-то ветку:
- 
- .
    ```
    ```
$ cat .git/HEAD
ref: refs/heads/main
```
    ```
- Когда вы выполняете команду `git checkout main`, Git просто записывает в `.git/HEAD` строку `ref: refs/heads/main`. Никакие файлы при этом не копируются.
- Если вы переключитесь на конкретный коммит, а не на ветку, `HEAD` начнёт указывать прямо на хеш коммита:
- 
- `git checkout a1b2c3d`
- При этом Git выведет предупреждение: `"You are in 'detached HEAD' state"`. Это значит, что новые коммиты не будут привязаны ни к одной ветке — и как только вы переключитесь на другую, найти их будет непросто. Чтобы выйти из этого состояния, просто создайте новую ветку, указывающую на текущий коммит: `git checkout -b new-branch`.
- Это можно представить так:
- 
- .
    ```
    ```
commit1 (a1b2) <- commit2 (c3d4) <- commit3 (e5f6) <- commit4 (g7h8)  [main]
                \
                 commit2.5 (i9j0) <- commit2.6 (k1l2)  [feature]
                                                          ^
                                                         HEAD

Содержимое файлов в директории .git/:

.git/HEAD ----------------> "ref: refs/heads/feature"
                                     |
                                     v
.git/refs/heads/feature ---------> "k1l2"
.git/refs/heads/main -----> "g7h8"
``` 
 
    ```
- 
- #### Теги — неподвижные указатели на коммиты
- В отличие от веток, всегда указывающих на последний коммит в цепочке, теги не перемещаются автоматически. Это вечные метки: ими удобно помечать стабильные версии проекта.
- 
- .
    ```
    ```
# Создать лёгий тег
git tag v1.0

# Создать аннотированный тег (с именем, почтой, комментарием)
git tag -a v1.0 -m "Релиз версии 1.0"
```
    ```
- Аннотированные теги хранятся как отдельные объекты в `.git/objects` и содержат метаданные. Легковесные теги — просто файлы с хешем коммита в директории `.git/refs/tags/`.
- Git не хранит информацию о том, откуда была создана каждая из веток. Ветки — это просто указатели на коммиты. Именно эта простота делает Git таким гибким.

- ## Работа с историей изменений
- Работая в DevOps или просто участвуя в сопровождении продакшн-систем, вы рано или поздно столкнётесь с вопросом:
    - «Когда это появилось?»
    - «Кто это поменял?»
    - «Почему оно сломалось?»
- Git позволяет отвечать на них без догадок, писем и долгих вечеров в Slack. История коммитов — ваш чёрный ящик: если научиться с ним работать, то можно быстро и точно восстанавливать ход событий.
- ### `git log`: хроника событий
- Базовая команда — `git log`. Она выводит историю коммитов от текущего к более ранним, показывая хеш коммита (уникальный SHA-1), автора, дату, сообщение коммита.
- Пример:
- 
- `git log --oneline`
- Что даст примерно такой результат:
- 
- .
    ```
    ```
9d04b6630 SSL: fixed build with BoringSSL, broken by 38a701d88.
38a701d88 SSL: ngx_ssl_set_client_hello_callback() error handling.
ac99f2808 Configure: MSVC compatibility with PCRE2 10.47.
a386df6b2 Version bump.
```
    ```
- Команда `git log` позволяет гибко фильтровать историю коммитов, ограничивая её только теми изменениями, которые затронули определённые файлы или каталоги. Для этого используется синтаксис с двойным дефисом `--`, который отделяет аргументы с опциями от списка путей к файлам. Например, `git log -- README.md` покажет только те коммиты, в которых был изменён файл `README.md`. Это особенно полезно, когда нужно отследить историю конкретного файла, выяснить, кто и когда внёс изменения, или найти источник ошибки в определённой части проекта.
- Двойное тире `--` необходимо, если имя файла может совпасть с названием ветки или опции. В простых случаях его можно опустить, но использование `--` делает команду однозначной и считается хорошей практикой.
- Фильтрацию можно комбинировать с другими параметрами для сужения поиска. Например:
    - `git log --author="Имя" -- README.md` — коммиты конкретного автора, изменившие `README.md`;
    - `git log --since="2024-01-01" --until="2024-12-31" -- src/` — все изменения в каталоге `src` за указанный период;
    - `git log -p -- main.py` — показать не только коммиты, но и сами изменения (патчи) в файле `main.py`.
- Такие комбинации делают `git log` мощным инструментом для анализа истории: от расследования причин поломки до подготовки релизных заметок.
- ### `git blame`: кто тронул эту строку?
- Иногда нужно узнать не только, когда изменился файл, но и кто добавил конкретную строку и при каких обстоятельствах. Для этого используют `git blame`.
- Например:
- 
- `git blame README.md`
- Вы получите построчную информацию вида:
- 
- .
    ```
    ```
b1e07409b1 (Michael Vernik 2024-08-31 22:42:09 -0700   1) <picture>
b1e07409b1 (Michael Vernik 2024-08-31 22:42:09 -0700   2)   <source media="(prefers-color-scheme: dark)" srcset="https://github.com/user-attachments/assets/9335b488-ffcc-4157-8364-2370a0b70ad0">
```
    ```
- `git blame` показывает, какой коммит внёс конкретную строку, кем он был сделан и когда.
- Важно помнить: `git blame` — это инструмент для диагностики и восстановления контекста, а не для поиска виноватых. В зрелой DevOps-культуре его используют, чтобы понять, как и почему произошло изменение.
- ### `git show`: раскрыть коммит
- Команда `git show <hash>` позволяет раскрыть содержимое коммита: какие файлы изменились, что добавилось, что удалилось.
- 
- `git show b1e07409b1`
- Это полезно, когда нужно понять логику изменений, особенно при работе с CI/CD и IaC, где мелкая правка YAML-файла может привести к остановке деплоя.

- ## Восстановление изменений: когда всё пошло не так
- ### Вариант 1: `git reset`
- Иногда вы что-то делаете, и всё ломается, иногда случайно удаляете нужный файл или хотите откатить изменения к предыдущей версии, и здесь на помощь приходит команда `git reset` — мощный, но опасный инструмент.  Главное правило: `reset` переписывает историю. С осторожностью используйте его на коммитах, которые уже кто-то мог забрать из общего репозитория.
- У `git reset` есть три режима, которые отличаются тем, насколько глубоко они "откатывают" изменения.
    1. `git reset --soft` — откатить коммит, но оставить всё в staging.
- Допустим, вы сделали коммит, но забыли добавить файл или хотите разбить один большой коммит на несколько:
- 
- `git reset --soft HEAD~1`
- HEAD переместится на один коммит назад, все изменения из удалённого коммита останутся в staging area, а рабочая директория не изменится.
- Вы можете сразу добавить недостающие файлы и выполнить команду `git commit` заново.
    1. **`git reset --mixed` (режим по умолчанию) — откатить коммит и убрать из staging.
- Самый частый сценарий: вы закоммитили не то и хотите вернуть изменения в рабочую директорию, чтобы переделать:
- 
- .
    ```
    ```
git reset HEAD~1
# или явно:
git reset --mixed HEAD~1
```
    ```
- HEAD переместится на один коммит назад, изменения из удалённого коммита останутся в рабочей директории (как неиндексированные правки), а staging очистится.
- Этот подход удобен, когда вы хотите отменить `git add` и сам коммит, но оставить наработки.
    1. `git reset --hard` — полностью стереть изменения (опасно!).
- Вы точно знаете, что всё, что было после определённого коммита, вам не нужно. Например, вы поэкспериментировали и хотите вернуть чистое состояние:
- 
- `git reset --hard HEAD~1`
- HEAD переместится на один коммит назад, все изменения (и в staging, и в рабочей директории) будут удалены.
- Рассмотренные примеры откатывают только один последний коммит, однако команды позволяют откатиться к любому коммиту в истории, указав его хеш вместо `HEAD~1`.
- ### Работа с конкретными файлами
- Если нужно сбросить только один файл, а не весь коммит:
- 
- .
    ```
    ```
# Убрать файл из staging, но оставить изменения в рабочей директории
git reset <hash> README.md

# Полностью откатить файл до состояния в последнем коммите (с потерей незакоммиченных правок!)
git checkout <hash> -- README.md
```
    ```

- ### Вариант 2: откатить коммит
- Если вы уже отправили изменения на сервер и хотите отменить его поведение (например, вернуть код в его изначальное состояние), можно использовать:
- 
- `git revert <hash>`
- Это создаст обратный коммит, который отменяет изменения, не ломая историю, — подходит для продакшна. В этом его главное отличие от `git reset`, переписывающего историю коммитов.
- 
- Случай
- Вы работаете над конфигурацией Nginx и случайно закоммитили в файле `nginx.conf` тестовую директиву, которая ломает сборку. Вы уже запушили коммит в общий репозиторий, где над проектом прямо сейчас работают ещё три разработчика. Нужно отменить изменения так, чтобы не переписывать историю и не создавать проблем коллегам, которые уже могли сделать `pull`. Какую команду вы используете?
- `git revert HEAD` 
- 
- Эта команда создаёт новый коммит, который отменяет изменения, внесённые последним коммитом. История остаётся неизменной, коллеги могут спокойно сделать `pull` и получить новый, корректирующий коммит.

- ## Git как инструмент расследования
- Представьте: к вам приходят с проблемой «пользователи не могут залогиниться из-за проблем с SSL перестали приходить события, раньше всё работало». В логах ничего внятного, а в коде ничего явного. Здесь выручает команда:
- 
- `git  log -p -S "SSL" src/event/ngx_event_openssl.c`
- Она показывает коммит, содержащий слово `SSL`, в файле, который отвечает за эту функцию. Посмотрев весь коммит, можно увидеть все изменения и при необходимости отменить их.
- Здесь Git работает как «временная» диагностика: вы смотрите не только на код, но и на его эволюцию — а это мощное преимущество в DevOps, где важна скорость реакции на баги.
- 
- Случай
- Ночью произошёл инцидент: приложение перестало обрабатывать запросы аутентификации. Вы посмотрели логи и поняли, что проблема связана с модулем `auth_module.c`. Но когда и почему изменилась логика работы с токенами? Вам нужно быстро найти причину и временно восстановить работоспособность, пока команда разбирается с корнем проблемы. Какие команды Git вы используете? Выберите все правильные варианты.
- 
- `git blame auth_module.c`
- Покажет, кто и когда изменял каждую строку в файле. Если проблема в конкретной строке с проверкой токена, вы сразу увидите автора и коммит, где это изменение появилось.
- 
- `git log -p -S "token_validate" -- auth_module.c`
- Найдёт все коммиты, в которых появлялась или исчезала строка `token_validate` в указанном файле. Это поможет определить, когда именно изменилась логика валидации.
- 
- `git show <hash>`
- Найдя подозрительный коммит с помощью `blame` или `log`, вы можете детально изучить его содержимое и понять, какие именно изменения были внесены и как они повлияли на аутентификацию.
- 
- `git checkout <parant_hash> -- auth_module.c`
- Если вы определили, что проблема началась после конкретного коммита, вы можете временно восстановить предыдущую версию файла локально, чтобы проверить гипотезу и вернуть работоспособность, пока готовится полноценный фикс.

- ## Культура коммитов
- Вы научились использовать историю Git как инструмент диагностики: `git log`, `blame`, `show`, `revert`. Но чтобы всё это действительно помогало, история должна быть читаемой. А это уже зависит от качества самих коммитов.
- Если история проекта — это журнал, то каждый коммит — отдельная запись. Чем она осмысленнее, тем проще вам и команде ориентироваться в изменениях через неделю, месяц или посреди ночного инцидента.
- ### Что делает коммит хорошим
- Хороший коммит: * охватывает одно логическое изменение (не «всё сразу»); * содержит понятное сообщение, объясняющее, что и зачем; * помогает быстро отследить причину изменений.
- Пример плохого коммита:
- 
- `update`
- Пример хорошего:
- 
- `fix(auth): устранён баг проверки токена при логине`
- Более подробно про оформление коммитов мы поговорим в финальном уроке модуля. А пока запомните: пишите сообщения понятно для других — это сильно упрощает работу с Git, когда всплывают проблемы. Хороший коммит — это вклад в командную культуру, прозрачность и поддержку DevOps-процессов.
- ## `.gitignore`: что не нужно хранить в репозитории
- Не всё, что находится в папке проекта, должно попадать в Git. Логи, скомпилированные файлы, конфигурации с паролями, временные файлы редактора раздувают репозиторий и могут создать проблемы при публикации. Чтобы не следить за ними при каждом коммите, можно перечислить их в специальном файле `.gitignore`.
- Файл `.gitignore` содержит список шаблонов (паттернов). Git проверяет каждый файл в рабочей директории и, если имя подходит под шаблон, игнорирует его — не показывает в `git status` и не добавляет при выполнении команды `git add`.
- Пример файла:
- 
- .
    ```
    ```
# Комментарии начинаются с решётки

# Игнорировать конкретный файл
.env

# Игнорировать все файлы с расширением .log
*.log

# Игнорировать папку целиком
node_modules/

# Игнорировать файлы в любой вложенности
**/temp/

# НЕ игнорировать конкретный файл, даже если подходит под правило
!important.log
```
    ```

- ### Где должен лежать `.gitignore`?
- Обычно файл располагают в корне репозитория. Его нужно закоммитить — тогда правила будут действовать для всех, кто клонирует проект.
- Создавать файл `.gitignore` с нуля необязательно, можно использовать готовые коллекции. Популярный вариант — репозиторий [github.com/github/gitignore](https://github.com/github/gitignore), сборник файлов с шаблонами под многие языки и IDE.
- ## Практический кейс: базовый Git workflow
- Простая задача: вы DevOps-инженер, которому нужно поправить файл конфигурации приложения из Git. Цель — внести изменения, зафиксировать их и отправить в центральный репозиторий.
- Это минимальный порядок действий, который вы будете использовать в 90% случаев.
- Начнём с форка репозитория Nginx, с которым мы работали раньше. В UI проекта найдите слово `Fork` и нажмите на него. Создайте свой собственный форк с любым именем и приватностью на ваше усмотрение. Когда форк будет создан, у вас появится ссылка на его репозиторий.
- ### Шаг 1. Клонируем репозиторий
- Сначала необходимо получить код проекта на локальный компьютер:
- 
- .
    ```
    ```
git clone <ссылка на ваш репозиторий>
cd module1_nginx
```
    ```
- Теперь у вас есть локальная копия проекта со всей историей изменений.
- ### Шаг 2. Проверяем статус
- Посмотрим, какие файлы отслеживаются:
- 
- `git status`
- Если вы поменяете какой-то файл (например, `conf/nginx.conf`):
- 
- `vim conf/nginx.conf`
- Git сразу отобразит его в статусе как изменённый.
- ### Шаг 3. Фиксируем изменения
- Сначала добавим файл в staging area:
- 
- `git add conf/nginx.conf`
- Затем создадим коммит:
- 
- `git commit -m "fix(config): увеличено время таймаута до 30s"`
- ### Шаг 4. Отправляем изменения
- Переключаем дефолтную ветку main для работы с новым репозиторием:
- 
- .
    ```
    ```
# Посмотреть текущие удаленные репозитории
git remote -v
# Переключить внешний репозиторий origin на новый
git remote set-url origin <ссылка на ваш форк>
# Посмотреть что ветка origin смотрит на новый репозиторий
git remote -v
```
    ```
- Отправляем изменения в удалённый репозиторий:
- 
- `git push origin main`
- Если у вас есть доступ к записи — изменения попадут в центральный репозиторий, и коллеги смогут их видеть.
- С этим базовым набором знаний мы уже можем:
    - участвовать в реальных проектах,
    - отправлять изменения в shared-репозитории,
    - использовать Git для настройки CI/CD и инфраструктуры как код.
- Дальше мы научимся работать с ветками, организовывать фичи, решать конфликты и создавать merge request. Но основа для всего этого — те базовые операции, которые мы только что освоили.

- ## Ключевые мысли 
    1. Git — основа DevOps-практики. Он помогает командам работать согласованно, прозрачно и предсказуемо, устраняя silo-мышление и хаос ручного управления файлами.
    2. Принцип Codebase реализуется через Git. Один репозиторий — один источник правды. Это фундамент для автоматизации, CI/CD и инфраструктуры как код.
    3. Git — распределённая система. У каждого разработчика есть полный клон истории проекта. Это даёт гибкость, автономию и устойчивость к сбоям.
    4. Модель Git основана на трёх состояниях: рабочая директория, staging, коммиты. Это позволяет точно контролировать, что попадёт в историю и в каком виде.
    5. Git хранит не дельты, а снимки. Каждый коммит — это зафиксированное состояние проекта, с уникальным хешем и привязкой к автору и времени.
    6. История коммитов — это инструмент анализа и отладки. С помощью `log`, `blame`, `show`, `checkout` можно расследовать изменения, находить причины багов и восстанавливать файлы.
    7. Культура коммитов — неформальная, но критически важная часть инженерной культуры. Хороший коммит — понятный, атомарный, осмысленный. Он помогает команде и самому автору через неделю или месяц понять, что и зачем было сделано.
    8. Git уже полезен даже при начальных навыках работы с ним. Базовый рабочий цикл `clone → edit → add → commit → push` покрывает многие реальные задачи в DevOps.
