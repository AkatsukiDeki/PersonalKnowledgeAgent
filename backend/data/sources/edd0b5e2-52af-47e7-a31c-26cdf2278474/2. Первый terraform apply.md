## Язык разметки HCL

Желаемое состояние инфраструктуры декларативно описывается в файлах с расширением `.tf` с использованием языка разметки [HCL](https://developer.hashicorp.com/packer/docs/templates/hcl_templates/syntax) (HashiCorp Configuration Language). Он похож на JSON, но более нагляден; его используют все инструменты Hashicorp.

Манифест HCL состоит из блоков. Каждый блок описывает определённую сущность и её свойства. Например:

```
тип_блока "вид_описываемой_сущности" "имя_сущности"{
 # решётка — это комментарий;
 # "имя_сущности" — опциональный параметр, иногда его нет.
 
 // кстати, два слеша — это тоже комментарий.
 
 # ниже описаны атрибуты блока
 # в отличие от JSON, HCL не требует фигурных скобок вокруг атрибутов и использует знак равенства вместо двоеточия.
 ключ1 = значение1 
 ключ2 = значение2
} 
```

Основные **верхнеуровневые** блоки в Terraform (в одном каталоге модуля):

- `terraform` — настройки самого Terraform: ограничения версии CLI и провайдеров, бэкенд для state, эксперименты. Это не описание «железа» в облаке.
- `provider` — как подключаться к API платформы (учётка, регион/зона по умолчанию, эндпоинты). Один провайдер может обслуживать много ресурсов.
- `resource` — создание и управление сущностью в инфраструктуре (ВМ, сеть, диск и т.д.); Terraform будет приводить реальное состояние к описанному в блоке.
- `data` — только чтение: ссылка на уже существующие объекты или внешние данные без обязательного управления ими из этого манифеста (часто — чтобы подставить ID в `resource`). Подробнее — в блоке ниже.
- `variable` — входные параметры модуля; значения задаются через CLI, файлы `.tfvars`, CI и т.д. Подробнее — в следующих уроках.
- `locals` — локальные вычисляемые значения внутри модуля: удобно собрать имя, список зон или повторяющееся выражение в одном месте, не создавая ресурс в облаке.
- `output` — что вернуть наружу после `apply`: IP, ID, DNS — для человека, для другого стека Terraform или для скриптов.
- `module` — подключение другого каталога с конфигурацией как кирпича: переиспользование и композиция. Разберём отдельно.

### Источники данных (`data`)

Блок `data` задаёт запрос к API провайдера на чтение. При `terraform plan` и `apply` Terraform получает актуальные поля объекта в облаке (например, `id`, `v4_cidr_blocks`, зону) и делает их доступными в выражениях. Запись в state для `data` не означает «мы владеем этим ресурсом». `terraform destroy` **не удалит** объект только потому, что вы его прочитали через источник данных.

Это нужно, когда подсеть, сеть или образ уже существуют (созданы в другом стеке, вручную или другой командой), а в текущем манифесте нужно подставить их идентификаторы в `resource`, не дублируя длинные UUID в каждом месте и не храня их «магическими строками».

Синтаксис тот же, что у `resource`: `data "<тип_источника>" "<локальное_имя>" { ... }`. На локальное имя ссылаются так: `data.<тип>.<имя>.<атрибут>`.

Например, можно взять уже существующую подсеть по её идентификатору и передать её `id` в сетевой интерфейс виртуальной машины:

```
data "yandex_vpc_subnet" "existing" {
  subnet_id = "<идентификатор-подсети-в-облаке>"
}

resource "yandex_compute_instance" "vm" {
  # ... остальные аргументы ВМ ...

  network_interface {
    subnet_id = data.yandex_vpc_subnet.existing.id
  }
} 
```

Здесь `existing` — произвольное имя внутри конфигурации. По нему строится ссылка `data.yandex_vpc_subnet.existing.id`. В том же провайдере часто используют, например, `data "yandex_compute_image"` (получить `image_id` по семейству образов). В финальной практике спринта вы увидите такие же ссылки на результаты `data` — заранее имеет смысл запомнить форму `data.<тип>.<имя>.<атрибут>`.

Полный перечень источников и их аргументов — в [документации провайдера Yandex Cloud](https://terraform-provider.yandexcloud.net/) в разделе **Data sources**.

Внутри блоков (например, у `resource "yandex_compute_instance" "vm"`) часто встречаются **вложенные блоки** — `boot_disk { ... }`, `network_interface { ... }`: это отдельная синтаксическая конструкция, не «присвоение через `=`».

Чтобы не запутаться, полезно помнить разницу между этими блоками. `variable` — значение приходит извне (аргументы модуля, `.tfvars`), `output` — значение уходит наружу после успешного применения. `locals` живёт только в конфигурации и state не «размножает» новыми облачными объектами. `data` не объявляет намерение создать ресурс — в отличие от `resource`, хотя в плане оба могут вызывать API для чтения.

Подробное описание ресурсов и их атрибутов для Яндекс Облака можно найти в [документации провайдера](https://terraform-provider.yandexcloud.net/).

## Провайдеры Terraform

Terraform создаёт инфраструктуру с помощью **провайдеров** — компонентов, которые отвечают за «связь» c API облака. Их можно воспринимать как «драйверы»: они преобразуют манифест в конкретные действия — создание, изменение или удаление ресурсов.

Провайдеры обычно предоставляются самой платформой или сообществом. Например, провайдер Яндекса позволяет взаимодействовать с Яндекс Облаком.

Процесс применения изменений можно разделить на несколько шагов:

1. **Определить желаемое состояние ресурса** — Terraform анализирует конфигурацию ресурса (`.tf`-файлы) и определяет, какими параметрами он должен обладать.
2. **Определить текущее состояние ресурса** — Terraform через провайдера получает информацию о текущем состоянии ресурса из облачной платформы или использует данные из файла состояния. Про него мы поговорим в следующих уроках. Пока важно понимать, что Terraform сохраняет сведения о созданных ресурсах в специальном служебном файле.
3. **Определить, нужны ли изменения** — Terraform сравнивает желаемое состояние ресурса (из манифеста) с текущим (полученным на предыдущем шаге) и определяет, требуется ли создание, изменение или удаление.
4. **Применить изменения** — если изменения действительно нужны, Terraform вызывает API облачной платформы через провайдер и выполняет нужные операции.

При работе Terraform придерживается принципа идемпотентности. То есть **повторный запуск не создаёт дубликаты сущностей**, если они уже есть. Утилита вносит только необходимые изменения, чтобы привести инфраструктуру к описанному состоянию.


**Случай**

- Упорядочьте этапы, через которые проходит Terraform перед внесением изменений в инфраструктуру.

1. **Проанализировать конфигурацию ресурсов и определить желаемое состояние**
    
2. **Получить информацию о его фактическом состоянии**
    
3. **Сопоставить ожидаемое и текущее состояние, выявив необходимость изменений**
    
4. **Выполнить операции, если корректировки действительно требуются**

### Практика: конфигурация провайдера

Ресурсы Teraform могут быть недоступны на территории РФ. Чтобы обойти ограничения, можно настроить зеркало от Яндекса.

```
sudo apt update
sudo apt install -y wget unzip

TF_VERSION=1.9.8
TF_ARCHIVE="terraform_${TF_VERSION}_linux_amd64.zip"

wget -O "$TF_ARCHIVE" "https://hashicorp-releases.yandexcloud.net/terraform/${TF_VERSION}/${TF_ARCHIVE}"
unzip -o "$TF_ARCHIVE"
sudo mv terraform /usr/local/bin/
rm "$TF_ARCHIVE" 
```

Этот код скачивает Terraform CLI с зеркала Яндекса.

Посмотрите файл `~/.terraformrc` на ВМ:

```
provider_installation {
  network_mirror {
    url = "https://terraform-mirror.yandexcloud.net/"
    include = ["registry.terraform.io/*/*"]
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
} 
```

Разберём блок `provider_installation` из конфигурации Terraform построчно:

- `provider_installation` — начало блока конфигурации, определяющего, как Terraform должен устанавливать провайдеры;
- `network_mirror` — указывает, что провайдеры следует загружать из сетевого зеркала (локального репозитория), а не напрямую из официального реестра;
- `url = "https://terraform-mirror.yandexcloud.net/"` — адрес зеркала;
- `include = ["registry.terraform.io/*/*"]` — инструкция загружать из зеркала только те провайдеры, которые в оригинале размещены на `registry.terraform.io`.

Синтаксис `*/*` означает:

- первая `*` — любое имя провайдера (например, `yandex`, `aws`);
- вторая `*` — любая версия или подмодуль.

Иными словами, зеркало обслуживает все провайдеры с официального реестра. `direct {` определяет правила для прямого подключения к источникам провайдеров (минуя зеркало). Здесь мы задаём исключения.  
`exclude = ["registry.terraform.io/*/*"]` запрещает Terraform напрямую обращаться к `registry.terraform.io` за провайдерами. Все запросы к официальному реестру будут перенаправлены на зеркало.

Этот конфиг часто используют в корпоративной среде: он позволяет централизованно управлять версиями, снижает риск случайных загрузок из интернета и помогает поддерживать согласованность окружений.

Подробнее про конфигурацию `.terraformrc` можно узнать в [документации](https://developer.hashicorp.com/terraform/cli/config/config-file).

Далее **склонируйте на машину репозиторий, который создавали ранее**, и создайте файл `main.tf` в рабочей директории, где вы укажете настройки провайдера:

```
terraform {
  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      # Можно указать версию провайдера, с которой будет работать конфигурация.
      version = ">= 0.87.0"
    }
  }
  # Также можно указать версию CLI Terraform.
  required_version = ">= 0.13"
}

# Зона доступности (Availability Zone), где по умолчанию будут создаваться все ресурсы:
provider "yandex" {
  zone      = "ru-central1-a"
} 
```

Это важная часть конфигурации. Здесь мы указываем `required_providers` — Terraform понимает, что для работы нужно скачать провайдер `yandex-cloud/yandex`. Без него код не будет работать, потому что именно провайдер «переводит» описание ресурсов в запросы к API облака.

Отсюда следует, что версия провайдера имеет значение. В конфиге указано, что она должна быть не ниже `0.87.0`.

Разные версии провайдеров могут заметно отличаться. Например, в версии `0.0.1` может не быть поддержки Kubernetes, потому что такая возможность появилась только в версии `0.0.5`.

Кроме того, в новых версиях исправляют ошибки, меняют поведение ресурсов и иногда помечают часть параметров или ресурсов как устаревшие (deprecated). Поэтому важно обращать внимание на версию провайдера, читать документацию и использовать ту, которая подходит под вашу задачу.

### Почему важно контролировать версию провайдера

Может показаться, что лучше всегда использовать последнюю версию провайдера. Но на практике это не всегда безопасно: новые версии могут содержать изменения, из-за которых часть вашего Terraform-кода перестанет работать.

Особенно это касается мажорных обновлений (например, перехода с `1.x` на `2.x`) — в них часто встречаются несовместимые изменения.

Именно для этого в Terraform есть несколько способов указать версию провайдера (и модулей) в поле `version`. Они позволяют гибко задавать допустимые диапазоны. Разберём основные.

**1. Базовые операторы сравнения**

Terraform поддерживает стандартные операторы:

- `>= 0.87.0` — версия не ниже `0.87.0`;
- `<= 0.90.0` — версия не выше `0.90.0`;
- `> 0.87.0` — строго больше;
- `< 0.90.0` — строго меньше;
- `= 0.87.0` или просто `0.87.0` — точная версия.

Пример:

```
version = ">= 0.87.0, < 0.90.0"  # от 0.87.0 до 0.89.x 
```

**2. Тильда (`~>`) — «пессимистичный» диапазон**

Синтаксис:

```
version = "~> 0.87.0" 
```

Разрешает обновления, не затрагивающие мажорную и минорную версию. Проще всего запомнить так: Terraform будет обновлять версию, но только в рамках той же ветки.

Например:

- `~> 0.87.0` — можно обновляться до `0.87.1`, `0.87.2`, но не до `0.88.0`;
- `~> 1.2.0` — можно обновляться до `1.2.x`, но не до `1.3.0`.

Это удобно, когда нужно получать патчи (исправления ошибок), но избегать изменений API или новых функций, которые могут сломать совместимость.

**3. Комбинации условий**

Можно задавать несколько условий через запятую — Terraform воспринимает их как логическое «И».

Примеры:

`">= 0.87.0, < 0.90.0"` — диапазон версий; `">= 0.87.0, ~> 0.87.5"` — не ниже `0.87.0` и в рамках `0.87.x` (эквивалентно `~> 0.87.5`); `"~> 0.87.0, != 0.87.3"` — `0.87.x`, но не `0.87.3` (если известна проблемная версия).

**4. Специальные значения**

`""` (пустая строка) — разрешает любую версию (не рекомендуется для продакшена); `"latest"` — использует последнюю доступную версию (рискованно: может сломать совместимость); `"*"`, `"x"` — аналогично `""` (любая версия).

**5. Диапазоны с мажорными версиями**

`">= 1.0.0"` — любые версии начиная с `1.0.0` (`1.0.1`, `2.0.0`, `3.5.2` и т.д.); `"< 2.0.0"` — только версии до 2.0.0 (`1.9.9`, `1.5.0`, но не `2.0.0`).

### Требование к версии Terraform CLI

`required_version` задаёт требование к версии Terraform CLI. Это нужно, чтобы гарантировать совместимость:

- синтаксических конструкций (например, `for_each`, `dynamic`);
- функции в HCL (язык конфигурации);
- поддержку новых провайдеров и их фич.

Если версия CLI ниже необходимой, могут появляться ошибки вида `unknown block type` и `function not found`.

Следите за версиями провайдеров и Terraform CLI. Перед обновлением полезно посмотреть changelog: там видно, какие изменения могут повлиять на ваш код.

Это помогает заранее понять, что может сломаться, и избежать неожиданных проблем при запуске.

Конфигурация провайдера завершена, далее мы приступим к настройке аутентификации в облаке. Не забывайте по ходу работы делать коммиты и сохранять наработки в GitLab.

### Аутентификация в облаке и настройка YC

Чтобы провайдер Terraform мог отправлять запросы на управление инфраструктурой, нужно аутентифицироваться в облаке. Один из вариантов — сделать это через консольный клиент.

Для работы с Yandex Cloud нам потребуется утилита `yc` — официальный интерфейс командной строки (CLI) для управления сервисами Yandex Cloud. Она позволяет взаимодействовать с облачной платформой без использования веб-консоли, автоматизировать задачи и интегрироваться в CI/CD-процессы.

Нам нужно пройти аутентификацию от имени [федеративного пользователя](https://yandex.cloud/ru/docs/iam/concepts/users/accounts#saml-federation) .


**Что такое «федеративная авторизация»?**

**Федеративная авторизация** — механизм, позволяющий пользователям получать доступ к облачным сервисам с использованием внешней системы аутентификации (например, корпоративного Active Directory или любого OIDC-провайдера). Это устраняет необходимость создания отдельных учетных записей в каждом облаке — очень распространённое решение в корпоративном мире.


### Практика: аутентификация в облаке

Убедитесь в том, что `yc` установлен, командой:

```
yc --version 
```

Если нет, установите `yc` [по инструкции](https://yandex.cloud/ru/docs/cli/operations/install-cli).

Далее нужно пройти аутентификацию.

Обратите внимание, что мы используем виртуальную машину без графического интерфейса. Это очень распространённая практика, так как не нужно тратить ресусы ВМ на GUI. Но для настройки окружения нужно выполнить [подготовительные шаги](https://yandex.cloud/ru/docs/cli/operations/authentication/federated-user#linux-vm-auth).

Затем создайте на ВМ файл `/usr/local/bin/xdg-open` со следующим содержимым:

```
#!/bin/sh
echo $* > /dev/tty 
```

Назначьте права на исполнение файла:

```
sudo chmod +x /usr/local/bin/xdg-open 
```

Далее приступаем к настройке `yc`:

```
yc init --federation-id=<идентификатор_федерации> 
```

ID федерации практикума:

```
bpfsvjbobkj5c5c46rht 
```

Сохраните полученную ссылку согласно инструкции — она пригодится далее.

Пробросьте ssh-порт на свою локальную машину командой:

```
ssh -L <порт>:127.0.0.1:<порт> <имя_пользователя>@<IP-адрес_ВМ> 
```

Порт нужно взять из полученной ссылки. Он неочевидно спрятан в параметре url: `...redirect_uri=http%3A%2F%2F127.0.0.1%3A42121%2...`. `42121` — это нужный порт. Порт каждый раз меняется.

Теперь перейдите по полученной ссылке и пройдите аутентификацию в браузере. После успешной аутентификации вернитесь в консоль и настройте профиль, выбрав фолдер своей когорты. Вам может потребоваться [Cloud ID](https://yandex.cloud/ru/docs/resource-manager/operations/cloud/get-id) и [Folder ID](https://yandex.cloud/ru/docs/resource-manager/operations/folder/get-id) — их можно увидеть на главной странице веб-консоли облака.

Зону доступности можно выбрать `ru-central1-a`. Если `yc` отработает успешно — значит, авторизация прошла корректно.

### IAM-токен

Один из способов аутентифицировать провайдер Terraform в API Облака — использовать IAM-токен.

**IAM-токен** (Identity and Access Management Token) — это **временный ключ аутентификации**, применяемый облачными платформами для безопасного доступа к API и сервисам без использования паролей. Он содержит информацию о правах доступа и действует ограниченное время.

В Яндекс Облаке срок жизни токена — не более 12 часов. По истечении срока токен нужно будет выписать заново. Это распространённая практика.

Подробнее про токен можно узнать в [документации](https://yandex.cloud/ru/docs/iam/concepts/authorization/iam-token).

---

### Практика: получение IAM-токена

Получить токен можно командой:

```
yc iam create-token 
```

Но гораздо проще сразу заполнить все переменные окружения, которые нужны для работы Terraform. Это токен, `folder_id` и `cloud_id`:

```
export YC_TOKEN=$(yc iam create-token)                     
export YC_CLOUD_ID=$(yc config get cloud-id)
export YC_FOLDER_ID=$(yc config get folder-id) 
```

Выполните команду выше и убедитесь, что переменные установились. Проверить это можно командой:

```
printenv | grep "YC" 
```

Обратите внимание

Переменные будут активны для текущего сеанса терминала. Для нового сеанса их можно пересоздать теми же командами.

Заключительный этап. Выполните инициализацию провайдера командой:

```
terraform init 
```

Вывод консоли `"Terraform has been successfully initialized!"` означает, что Terraform инициализировал провайдер и готов к работе.


### Что происходит при инициализации проекта

При выполнении `terraform init`, консольный клиент скачивает указанные в манифестах провайдеры в скрытую директорию `.terraform`. Вывод команды `tree .terraform`:

Где `terraform-provider-yandex_v0.171.0` — это бинарный файл провайдера.

Хорошей практикой будет сразу создать файл `.gitignore` и добавить эту [директорию и прочие служебные файлы](https://github.com/github/gitignore/blob/main/Terraform.gitignore) в исключение.

Обратите внимание на файл `.terraform.lock.hcl` в рабочей директории — он фиксирует текущие зависимости версий провайдеров.

## Первые шаги запуска инфраструктуры

Настроив провайдера и получив токен для аутентификации, мы готовы разворачивать инфраструктуру с помощью Terraform. Как мы обсуждали выше, для описания используется язык разметки HCL в файлах расширения `*.tf`. Чаще всего центральным местом описания инфраструктуры выступает файл `main.tf`, однако это не обязательное требование. Terraform читает все файлы `*.tf` и самостоятельно выстраивает зависимости манифестов.

Развернём виртуальную машину в Яндекс Облаке. Для этого мы опишем ресурс типа `yandex_compute_instance`. Внутри ресурса заполним основные параметры ВМ:

- `name` — имя машины.
- `resources` — количество ядер и оперативной памяти.
- `scheduling_policy` — политика размещения машины: в данном случае она прерываемая и может перезапускаться раз в сутки, что подходит для тестовых и некритичных приложений и экономит бюджет.
- `boot_disk` — загрузочный диск. Здесь указывается образ операционной системы.
- `network_interface` — идентификатор подсети, к которой будет подключена ВМ.
- `metadata` — SSH-ключ для доступа к ВМ.
- `allow_stopping_for_update` — параметр, который позволяет останавливать машину при изменении конфигурации — пригодится в дальнейшем.

Подробнее про ресурс [yandex_compute_instance](https://yandex.cloud/ru/docs/terraform/resources/compute_instance).

Далее нам потребуются команды:

- Для проверки синтаксиса на ошибки:

```
terraform validate 
```

- Для приведения конфигурационных файлов Terraform (`.tf`, `.tfvars`) к единому стилю, чтобы улучшить читаемость (команда правит отступы, кавычки, скобки и запятые):

```
terraform fmt 
```

- Просмотр планируемых изменений:

```
terraform plan 
```

- Применение изменений:

```
terraform apply 
```

Приступим к практике.

### Практика: запуск виртуальной машины

Допишите в файл `main.tf` следующую конфигурацию:

```
# Тип блока, тип ресурса, имя блока
resource "yandex_compute_instance" "vm-1" {
    name = "lesson-terraform-<Ваш логин>"
    resources {
        cores  = 2
        memory = 2
    }

    scheduling_policy {
        preemptible = true
    }

    boot_disk {
        initialize_params {
            image_id = "<Ваш image id>"
        }
    }

    network_interface {
        subnet_id = "<Ваш subnet id>"
        # Параметр nat включает присвоение публичного IP машине.
        nat       = false
    }

    metadata = {
        ssh-keys = "ubuntu:${file("~/.ssh/id_rsa.pub")}"
    }
    
    allow_stopping_for_update = true
} 
```

Заполните значения идентификаторов `image_id` и `subnet_id`. Их можно узнать как в веб-интерфейсе консоли облака, так и с помощью утилиты командной строки `yc`.

Получить список подсетей можно так:

```
yc vpc subnets list 
```

Поиск подходящего ID образа, например для Ubuntu 22.04:

```
yc compute image list --folder-id standard-images | grep ubuntu-22-04-lts 
```

Выбрать можно любой, но лучше взять свежий. Например, версия от `2025.05.19`: `fd845dr9j4h2aaq1m6ko`

И не забудьте про публичный ssh-ключ. С его помощью можно подключиться к поднятой ВМ. Ключ нужно поместить локально по указанному пути из манифеста `~/.ssh/id_rsa.pub`, чтобы Terraform добавил его на созданную ВМ.

Выполните команду:

```
terraform validate 
```

Вывод `"Success! The configuration is valid."` говорит о том, что всё готово к запуску.

Выполните команду, чтобы посмотреть на планируемые изменения:

```
terraform plan 
```

Убедившись, что это именно те изменения, которые мы описывали в манифесте, примените их командой:

```
terraform apply 
```

Далее Terraform с помощью провайдера Яндекса отправит запросы в API облака для создания ВМ.

Вы увидите следующий вывод:

```
yandex_compute_instance.vm-1: Creating...
yandex_compute_instance.vm-1: Still creating... [10s elapsed]
yandex_compute_instance.vm-1: Still creating... [20s elapsed]
yandex_compute_instance.vm-1: Still creating... [30s elapsed]
yandex_compute_instance.vm-1: Still creating... [40s elapsed]
yandex_compute_instance.vm-1: Creation complete after 43s [id=fhmuo...]

Apply complete! Resources: 1 added, 0 changed, 0 destroyed. 
```

Виртуальная машина создана!

Найти свою машину можно либо в облачной веб-консоли, либо с помощью `yc`:

```
yc compute instance list | grep lesson-terraform-<Ваш логин> 
```

Будет ли виртуальная машина создана заново при изменении параметра `nat` в манифесте?

Провайдер старается избегать деструктивных изменений. Если параметр можно изменить «на горячую», удаление и пересоздание ресурса не выполняются.


### Удаление инфраструктуры

Подход IaC с использованием Terraform позволяет прозрачно управлять инфраструктурой и вносить изменения. Мы всегда знаем, какой ресурс и как изменится в результате наших действий. Кроме того, IaC позволяет быстро масштабировать инфраструктуру и копировать среды.

Перед выполнением команды удаления, вы увидите список ресурсов, которые будут удалены. Это будут только те ресурсы, которые вы описывали в `*.tf`-файлах. Это одно из преимуществ подхода IaC и использования Terraform: можно легко удалить всю созданную инфраструктуру, не затрагивая другие ресурсы.

### Практика: удаление машины

Удалите машину командой:

```
terraform destroy 
```

Внимание

Периодически в конце уроков мы будем предлагать вам удалить созданные в облаке тестовые сущности с помощью `terraform destroy`. Если вы сразу переходите к следующему уроку, делать это не обязательно — там мы отдельно укажем, если эти сущности ещё понадобятся. В противном случае вы всегда сможете развернуть их заново из кода в Git и заодно повторить материал.

Главное — не забывайте сохранять код в Git: это одна из ключевых идей подхода IaC.

Убедитесь, что ВМ удалена с помощью команд `yc` из прошлых заданий.
