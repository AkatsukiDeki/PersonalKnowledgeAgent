
В прошлом уроке мы разобрали переменные, рассмотрели как они помогают подстраивать манифесты под разные задачи и окружения. Поговорили о том что делать, если бизнес вырос и одной виртуальной машины или одного окружения уже недостаточно. Напомню, что мы пришли к тому, что копировать блок `resource` в манифесте нужное количество раз не самое хорошее решение, которое приведёт к очевидным проблемам. Такой подход нарушает принцип DRY (Don’t Repeat Yourself, "не повторяй сам себя"), критически важный для инфраструктурного кода. Ведь плодя файлы с разными описаниями одинаковых и схожих ресурсов мы получаем:

1. **Риск рассинхронизации:** при изменении параметра легко пропустить одну из копий. 2. **Сложность ревью:** нужно проверять в коде, что все копии на всех окружениях идентичны. 3. **Проблемы с Git:** при откате изменений легко потерять консистентность, потому что будет изменяться не код целиком, как часть gitflow, а части разных файлов.

Нам осталось сделать еще буквально шаг до того, чтобы свободно деплоить большие инфраструктуры и управлять ими. Дело в том что даже обернув значения нужных нам литералов в переменные, настроив input и output мы не уйдем от множества файлов. Решением, которое может помочь справиться с этой задачей - управляющие конструкции:

- **условные операторы**,
- **циклы**,
- **динамические блоки**.

Они облегчают работу с Terraform, делают конфигурации более гибкими, масштабируемыми и удобными для поддержки. Так же освобождают нас от необходимости переписывать (или копировать) ресурсы/переменные и другие сущности Terraform внутри или снаружи модуля.

Разберём подробнее.

## Условные операторы

Переменные из прошлого урока задают **входные данные**, но часто нужно по-разному **интерпретировать** этот вход: включить диск только в `prod`, выбрать образ в зависимости от флага, подставить значение по умолчанию, если параметр не передали. Для таких ветвлений в Terraform нет привычных блоков `if` / `else`, как в языках общего назначения. Вместо них используется **тернарный оператор** — единственная «условная конструкция» в выражениях HCL. Тернарная условная опера́ция (от лат. ternarius — "тройной") — это реализованная во многих языках программирования операция, возвращающая второй или третий операнд в зависимости от значения логического выражения, заданного первым операндом.

Сначала вычисляется условие (оно должно давать `bool`), затем берётся либо левая ветка (истина), либо правая (ложь). Оба результата должны быть **совместимы по типу** с контекстом, куда подставляется выражение.

Синтаксис:

```
condition ? value_if_true : value_if_false 
```

**Пример из практики:** при создании ВМ удобно подставить публичный SSH-ключ из файла на машине разработчика, а если файла нет — не падать на этапе парсинга, а подставить заглушку (или другое согласованное с командой значение), чтобы явно увидеть проблему в метаданных:

```
metadata = {
  ssh-keys = "ubuntu:${                                     /* Строка для cloud-init или метаданных: пользователь и ключ в одном поле */
    fileexists(pathexpand("~/.ssh/id_rsa.pub")) ?           /* Условие: существует ли файл ключа после раскрытия ~ */
    file(pathexpand("~/.ssh/id_rsa.pub")) :                 /* Если да — читаем содержимое ключа */
    "SSH_KEY_NOT_FOUND"                                     /* Если нет, то вывод что ключа нет */
  }"
} 
```

Обратим внимание на то, что можно записать тернарный оператор не в одну строку, но и с переносами, что бывает удобно. Здесь важно различать **проверку** (`fileexists`) и **чтение** (`file`): при отсутствии файла вызов `file(...)` без условия привёл бы к ошибке при планировании.

Тернарный оператор сочетают с переменными из прошлого урока - условие часто строят на `var.*`, например `var.environment == "prod" ? ... : ...`. Также удобно отличать "значение не задано" (`null`) от осмысленного значения, задавать значения по умолчанию в одном выражении и связывать поля конфигурации без дублирования одних и тех же `resource`-блоков.

Тернарный оператор хорошо решает задачи "включить / выключить" или «выбрать одно из двух», но **масштабировать** инфраструктуру им неудобно: десять одинаковых ВМ не опишешь без перечисления или копирования. Для повторяющихся ресурсов нужны **циклы**.

## Циклы

Как мы уже сказали во вступлении, циклы в Terraform позволяют создавать **несколько экземпляров** одного ресурса (или модуля), не размножая блоки `resource` вручную. Это и есть практическое продолжение идеи DRY: одно объявление - много объектов в state.

Ниже — три разных механизма: `count` и `for_each` привязаны к **ресурсам**, выражение `for` — к **значениям** (в `locals`, `output` и т. д.). Их важно не путать.

### Цикл `count`

`count` — самый прямой способ: Terraform создаёт **ровно N копий** ресурса и нумерует их целыми индексами `0 ... N ... N-1`. Внутри блока доступен псевдоатрибут `count.index` (хранит порядковый номер текущей итерации).

Типичный пример — три однотипные ВМ, имена которых отличаются только суффиксом:

```
resource "yandex_compute_instance" "vm-1" {
  count = 3                                         /* Будут созданы три экземпляра с индексами 0, 1, 2 */
  name = "lesson-terraform-${count.index}"
  # ... остальная конфигурация ...
} 
```

В state и ссылках такие ресурсы адресуются по индексу в квадратных скобках (как элементы списка):

- `yandex_compute_instance.vm-1[0]` → name `lesson-terraform-0`;
- `yandex_compute_instance.vm-1[1]` → name `lesson-terraform-1`;
- `yandex_compute_instance.vm-1[2]` → name `lesson-terraform-2`.

В общем каталоге облака к шаблону имени стоит добавить уникальный префикс (как в примере с `for_each` и переменной `name_prefix`).

Часто `count` связывают с **длиной списка** из переменной: число машин совпадает с числом элементов, а имя берётся по индексу. **То есть через переменную.** Вместо «зашитой» тройки в `count = 3` берут **список имён** (или других параметров) из `variable`. Тогда Terraform сам посчитает, сколько ВМ нужно: столько, сколько строк в списке.

Здесь мы объявляем массив строк `vm_names`, а затем идём по нему циклом `count`, создавая набор ВМ с именами из массива и своим числовым индексом:

```
variable "vm_names" {
  type    = list(string)                      /* порядок элементов = порядок индексов count: 0, 1, 2, ... */
  default = ["vm-1", "vm-2", "vm-3"]
}

resource "yandex_compute_instance" "vm-1" {
  count = length(var.vm_names)                /* Сколько ВМ создать — ровно столько, сколько элементов в списке */
  name = var.vm_names[count.index]            /* У каждой копии свой count.index и имя совпадает с элементом списка с этим номером */
  # ... остальная конфигурация ...
} 
```

Как это читать по шагам:

1. В `terraform.tfvars` (или через `-var`) мы задаём `vm_names = ["vm-1", "vm-2", "vm-3"]`.
2. `length(var.vm_names)` даёт **3** — значит, будет **три** экземпляра ресурса `vm-1`.
3. У первого экземпляра `count.index` = **0**, у второго = **1**, у третьего = **2**. Имя ВМ берётся из списка с тем же номером: `vm_names[0]`, `vm_names[1]`, `vm_names[2]`.

В state это будет массив адресов: `yandex_compute_instance.vm-1[0]` с именем `vm-1`, `vm-1[1]` с именем `vm-2`, `vm-1[2]` с именем `vm-3`:

**Особенность поведения** `count` — привязка к позиции в списке. Индекс `0` всегда означает «первый элемент **текущего** `var.vm_names`». Если вставить новый элемент в начало или в середину, «смысл» каждого индекса сдвигается: Terraform сопоставляет state со старыми индексами и видит, что у существующих ресурсов должны измениться атрибуты (например, `name`). В плане это часто выглядит как **изменение** нескольких экземпляров и добавление одного нового, а не создание ещё одной ВМ:

Пример: добавили `extra-vm` в начало списка.

```
variable "vm_names" {
  type    = list(string)
  default = ["extra-vm", "vm-1", "vm-2", "vm-3"]
} 
```

Индексация изменилась теперь индекс `0` соответствует `extra-vm`, индекс `1` — бывшей «первой» ВМ и т. д.

Фрагмент `terraform plan` может выглядеть так:

```
Plan: 1 to add, 3 to change, 0 to destroy. 
```

Добавится новая ВМ, индексы остальных изменятся:

```
  # module.tf-yc-instance.yandex_compute_instance.vm-1[0] will be updated in-place
  ~ resource "yandex_compute_instance" "vm-1" {
        id                        = "fhmbgsefohqccifnsu8g"
      ~ name                      = "vm-1" -> "extra-vm"
    }

  # module.tf-yc-instance.yandex_compute_instance.vm-1[1] will be updated in-place
  ~ resource "yandex_compute_instance" "vm-1" {
        id                        = "fhmmq2eprvav675j0uuh"
      ~ name                      = "vm-2" -> "vm-1"
    }

  # module.tf-yc-instance.yandex_compute_instance.vm-1[2] will be updated in-place
  ~ resource "yandex_compute_instance" "vm-1" {
        id                        = "fhmjg7krvifa67t9ejn2"
      ~ name                      = "vm-3" -> "vm-2"
    } 
```

Официальная документация по `count`: [Meta-argument `count`](https://developer.hashicorp.com/terraform/language/meta-arguments/count).

Чтобы избежать описанной выше проблемы со сдвигом индексов, ресурсы часто привязывают к стабильному ключу (имени, идентификатору) с `for_each`.

### Цикл `for_each`

`for_each` создаёт экземпляры ресурса, у каждого своё имя в state: не `[0]`, `[1]`, а `["front"]`, `["back"]` — в зависимости от ключа. Аргумент `for_each` принимает **карту** (`map`) или **множество** (`set`). Обычный `list` напрямую сюда не подходит поэтому список строк удобно превратить в множество строк функцией `toset()`, чтобы элементы стали ключами.

**Имена в общем каталоге облака.** Если несколько студентов применяют один и тот же манифест в **одной папке** (каталоге), совпадающие значения `name` у ВМ, дисков и других ресурсов приведут к ошибке «имя уже занято» или к пересечению чужих ресурсов. Задайте **уникальный префикс** — например, свой логин — и подставляйте его в шаблон имени вместе с `${each.key}`:

```
variable "name_prefix" {
  description = "Уникальный префикс (логин), чтобы имена не пересекались с другими в общей папке"
  type        = string
}

variable "vm_names" {
  type    = list(string)
  default = ["front", "back"]
}

resource "yandex_compute_instance" "vm-1" {
  for_each = toset(var.vm_names)
  name     = "lesson-terraform-test-${var.name_prefix}-${each.key}"
  # ...остальная конфигурация...
} 
```

Значение `name_prefix` удобно задавать в `terraform.tfvars` (например, `name_prefix = "ivanov"`).

Здесь мы объявили переменную `vm_names`, содержащую список с именами машин, и с помощью конструкции `${each.key}` прошли по каждому значению. Внутри блока используют:

- `each.key` — ключ в `map` или элемент `set`;
- `each.value` — для `map` это значение по ключу, для `set` совпадает с `each.key`.

Если передать **карту объектов**, по `each.value` удобно получать поля.

Подробнее: [`for_each`](https://developer.hashicorp.com/terraform/language/meta-arguments/for_each).

**Когда что брать:** `count` — когда ресурсы действительно взаимозаменяемые и порядок фиксирован и неважен; `for_each` — когда важны **уникальные ключи**, меняется состав множества (добавили/убрали элемент), или у каждого экземпляра свой набор атрибутов из `map`.

### Цикл `for` (выражение)

Выражение `for` в квадратных или фигурных скобках **не создаёт ресурсы**. Оно строит новое значение — `list` или `map` из существующей коллекции. Так удобно готовить данные для `output`, `locals`, аргументов ресурсов и т. д.

Синтаксис для списка:

```
[for <элемент> in <коллекция> : <выражение>] 
```

Опционально добавляют фильтр: `... if <условие>`.

- `<элемент>` — временное имя для текущего значения при обходе;
- `<коллекция>` — `list` или `map` (при обходе `map` можно использовать форму с двумя переменными: `for k, v in ...`);
- результат — новый `list` (или `tuple`).

Пример: оставить только чётные числа.

```
output "even_numbers" {
  value = [for num in [1, 2, 3, 4] : num if num % 2 == 0]
} 
```

Здесь `num` пробегает по списку, условие `if num % 2 == 0` отсекает нечётные, итог — список `[2, 4]`.

Если обернуть выражение в **фигурные** скобки и использовать `=>`, получится **`map`**:

```
output "upper" {
  value = { for name in ["dev", "ops"] : name => upper(name) }
} 
```

- `["dev", "ops"]` — это **`list(string)`**, не `map`;
- `name => upper(name)` задаёт пары «ключ → значение»; ключом становится исходная строка, значением — `upper(name)`;
- итоговый тип — `map(string)`.

Документация: [`for` expressions](https://developer.hashicorp.com/terraform/language/expressions/for).


## Динамические блоки

Циклы — не единственный способ в Terraform сократить повторения и упростить конфигурацию. Для этого также используют механизм **динамической генерации блоков** - **вложенные** блоки одинаковой формы.

**`dynamic`** задаёт шаблон вложенного блока и источник элементов. Для каждого элемента коллекции Terraform сгенерирует отдельный вложенный блок с подставленными полями. Блок `dynamic` состоит из: цикла `for_each` (итерирует по коллекции) и `content` (описывает блок, который сгенерируется для каждого элемента):

```
dynamic "<имя_вложенного_блока>" {
  for_each = <коллекция>
  content {
    /* параметры блока */
  }
} 
```

Он особенно полезен, когда у ресурса есть множество однотипных вложенных блоков, отличающихся лишь значениями переменных. Например, такая конструкция:

```
dynamic "labels" {
  for_each = {
    environment = "prod"
    role        = "web"
    team        = "data-team"
  }
  content {
    key   = labels.key
    value = labels.value
  }
} 
```

- У `dynamic` аргумент `for_each` принимает те же типы, что и у ресурса: **`map` или `set`**. Коллекция может быть **пустой**: тогда Terraform **не сгенерирует ни одного** вложенного блока — это нормальное поведение, а не ошибка.
- Внутри `content { }` к текущему элементу обращаются как `<имя_dynamic>.key` / `<имя_dynamic>.value` (аналог `each.*`).

Пример: набор пар `key` / `value` вместо трёх ручных блоков.

без использования динамической генерации описывалась бы так:

```
labels {
  key   = "environment"
  value = "prod"
}
labels {
  key   = "role"
  value = "web"
}
labels {
  key   = "team"
  value = "data-team"
} 
```


Уточнение

_Уточнение:_ у метааргумента и у `dynamic` поля `for_each` тип — **`map` или `set`**, не список. Пустой список `[]` сюда не подойдёт; для «нет дисков» используют `{}` или `toset([])`.

**Краткая шпаргалка**

|Задача|Что использовать|
|---|---|
|Ветвление значения в выражении|Тернарный оператор `cond ? a : b`; при необходимости — `coalesce` / `try`|
|N однотипных ресурсов, порядок стабилен|`count`|
|Ресурсы по уникальным ключам, меняется состав|`for_each` (`map` или `set`)|
|Построить `list` / `map` для `output`, `locals`, аргументов|Выражение `for`|
|Много одинаковых вложенных блоков внутри ресурса|`dynamic` + `for_each` + `content`|
