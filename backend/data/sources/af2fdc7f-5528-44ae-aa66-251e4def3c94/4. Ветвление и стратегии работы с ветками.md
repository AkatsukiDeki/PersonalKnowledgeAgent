- В этом уроке мы коротко повторим, как устроены ветки в Git, и разберём базовые понятия — branch, HEAD, merge, rebase. Затем перейдём к стратегиям ветвления: Git Flow, GitHub Flow, GitLab Flow, trunk-based development. Поговорим о merge и rebase как о подходах к работе и посмотрим, как выбор стратегии влияет не только на структуру репозитория, но и на культуру, ритм и зрелость команды.
- 
- ### Основные термины ветвления в Git
- Ветки позволяют вести работу параллельно и без хаоса: десятки, а то и сотни разработчиков меняют код в одном репозитории и не мешают друг другу. Но чем больше гибкость, тем больше и ответственность: если неправильно выбрать стратегию ветвления — можно легко запутаться, потерять контроль или парализовать весь процесс доставки.
- Напомним, что ветка в Git — это указатель на последний коммит в цепочке. Вся история хранится в виде графа: коммиты — это узлы, каждый ссылается на родительский. Git не копирует файлы целиком, он работает со снапшотами изменений. Поэтому создание ветки занимает миллисекунды и не требует дополнительного места. Ветки в Git дешёвые, и это важно.
- Допустим, мы создаём ветку `feature/login-form`. Git просто создаёт новый указатель (ref), который ссылается на текущий коммит. С этого момента все наши новые коммиты будут двигать этот указатель вперёд. Основная ветка (`main`, `master`) при этом остаётся на месте, пока мы сами не решим объединить изменения.
- Перед тем как перейти к стратегиям, важно договориться о языке. В контексте Git есть несколько ключевых понятий, без которых разговор про ветки превращается в путаницу, — давайте их разберём.
- ### Branch и `HEAD`
- Branch (ветка, бранч) — это указатель на коммит. Мы можем представить его как ярлычок, приклеенный к определённой точке в истории. Когда мы коммитим, ярлычок сдвигается вперёд. Ветка — это не копия проекта, а просто ссылка.
- `HEAD` — это текущая позиция. Он указывает, где мы «находимся» в истории. Обычно он ссылается на ветку, а та — на коммит (но может и напрямую на коммит — detached HEAD).
- Допустим, мы инициализируем новый репозиторий и хотим создать ветку `feature/login-form`.
- 
- .
    ```
    ```
mkdir demo-repo && cd demo-repo
git init
echo "Hello" > hello.txt
git add . && git commit -m "initial commit"
```
    ```
- Теперь создадим ветку:
- 
- .
    ```
    ```
git branch feature/login-form
git checkout feature/login-form

Switched to branch 'feature/login-form'
```
    ```
- Добавим файл:
- 
- .
    ```
    ```
echo "<form></form>" > login.html
git add . && git commit -m "add login form"
```
    ```
- Посмотрим на граф веток:
- 
- .
    ```
    ```
git log --oneline --graph --all
* 453a443 (HEAD -> feature/login-form) add login form
* 1e84265 (main) initial commit
```
    ```
- master и main
- Сейчас Git активно переводит ветку по умолчанию с `master` на `main`. Некоторые сервисы уже создают ветку с новым названием, а другие — со старым. Мы будем использовать `main`, но если увидите, что `main` отсутствует — используйте `master`.
- Мы видим, что `feature/login-form` ушла вперёд от `main` (на одну строку выше) и содержит свой собственный коммит. Теперь переключимся обратно на `main` и ещё раз посмотрим на `git log`:
- 
- .
    ```
    ```
git checkout main
Switched to branch 'main'

git log --oneline --graph --all
* 453a443 (feature/login-form) add login form
* 1e84265 (HEAD -> main) initial commit
```
    ```
- Мы видим, что указатель `HEAD` перешёл с ветки `feature/login-form` на ветку `main`.

- ### Merge и rebase
- Разобравшись с основными понятиями, вернёмся к изучению других терминов.
- Merge Commit (коммит слияния) — это специальный коммит, который автоматически создаётся Git при выполнении слияния. В отличие от обычного коммита, у него два родителя (или более), что позволяет сохранить полную историю развития проекта. Он наглядно показывает, в какой момент произошло объединение веток, и позволяет легко откатить его при необходимости.
- Rebase — другой способ объединения. Вместо коммита слияния, Git «переписывает» историю так, будто ваши изменения изначально шли от нужной точки. Чище, но требует аккуратности, дальше в уроке мы подробнее разберёмся, как это работает.
- Pull Request/Merge Request (пулл-реквест, мёрж-реквест) - запрос на объединение одной ветки с другой. В нём видно, какие изменения попадут в код после слияния, ещё до того, как оно произойдёт. На этом этапе разработчики обычно проводят ревью кода и дают друг другу обратную связь.
- И merge, и rebase — не про «лучше/хуже». Merge — вы едете по своей дороге и в конце съезжаете на магистраль: на карте видны обе траектории. Rebase — переноситесь в начало магистрали и проезжаете путь по ней, словно отдельной дороги не существовало. В обоих случаях финиш один, но история путешествия (коммитов) будет разной.

- ## Зачем нужны стратегии ветвления?
- Когда у нас одна ветка — всё понятно. Но как только появляется команда, разные фичи, багфиксы, релизы и эксперименты, возникает вопрос: по каким правилам мы живём?
- Вот примеры проблем, которые возникают без стратегии:
    - ветка релиза содержит недоделанную фичу;
    - один разработчик перезаписывает изменения другого;
    - продакшн ломается, потому что кто-то случайно задеплоил незавершённую задачу;
    - мёрж-реквесты висят неделями, никто не понимает, что с ними делать.
- Хаос начинается, когда каждый работает по-своему. Стратегии ветвления — это договорённости, которые позволяют команде работать согласованно, избегать конфликтов и делать предсказуемые релизы.
- Рассмотрим несколько популярных стратегий ветвления. Начнём с Git Flow — одной из самых ранних и формализованных стратегий, появившейся в эпоху, когда релизы происходили реже, а команды искали чёткие процессы для управления параллельной работой.
- ### Git Flow
- Git Flow был предложен Винсентом Дриссеном (Vincent Driessen) в 2010 году и быстро стал популярным среди команд, которым нужно было управлять стабильностью, версионностью и процессом релизов. Стратегия исходит из идеи, что разные типы задач (фичи, хотфиксы, релизы) требуют разных рабочих процессов и потому должны вестись в разных ветках.
- В основе Git Flow лежат следующие ветки:
    - `main` — содержит только стабильные релизные версии.
    - `develop` — основная ветка для интеграции всех фич.
    - `feature/*` — ветки для разработки отдельных фич, создаются от `develop`.
    - `release/*` — ветки для подготовки релизов, создаются от `develop`, потом вливаются в `main` и `develop`.
    - `hotfix/*` — ветки для экстренных исправлений, создаются от `main`.
- Пример сценария:
- Команда работает над фичами в отдельных `feature/*`-ветках, и по мере завершения сливает их в `develop`. Когда наступает время релиза — создаётся ветка `release/*`, в ней происходит финальная подготовка: багфиксы, документация. После релиза эта ветка вливается в `main` (релиз) и в `develop` (чтобы не потерять багфиксы). Если в `main` всплывает критичная ошибка, делают `hotfix/*` и после исправления вливают его в обе ветки.
- Преимущества:
    - подходит для проектов с долгим циклом релизов,
    - чётко разграничивает типы задач и фазу работы,
    - упрощает поддержку стабильной версии и параллельной разработки.
- Недостатки:
    - много веток — сложно следить за синхронизацией;
    - merge-ад сложных случаев, особенно если разработка идёт в нескольких `feature`-ветках одновременно;
    - плохо подходит для Continuous Delivery, где релизы должны быть быстрыми и частыми.
- Git Flow можно сравнить с водопадной моделью разработки — он структурирован, последователен, но менее гибок. Для команд, которым нужно чёткое разделение стадий и стабильность на каждом этапе, это может быть хорошим стартом. Но для DevOps-культуры с быстрым ритмом изменений он часто оказывается слишком громоздким.

- ### GitHub Flow
- GitHub Flow — это минималистичная и современная стратегия, изначально предложенная командой GitHub. Она идеально подходит для проектов, где релизы происходят часто, а скорость обратной связи важна. В отличие от Git Flow, здесь нет ветки `develop`, нет релизных и хотфикс-веток. Всё проще: одна стабильная ветка (`main`) и короткоживущие ветки для фич.
- Как работает GitHub Flow:
    - Всё начинается с основной ветки `main`. Она всегда должна быть в рабочем состоянии — её можно деплоить в любой момент.
    - Для каждой задачи создаётся новая ветка (например, `feature/login-form` от `main`).
    - Работа ведётся в этой ветке. Периодически изменения пушатся, создаётся `pull request`.
    - Другие члены команды просматривают изменения, комментируют, предлагают улучшения. После одобрения и прохождения автоматических проверок ветка вливается обратно в `main`. Лучше всего, когда после слияния происходит автоматический деплой.
- Преимущества:
    - простота и минимум сущностей: одна основная ветка, короткие `feature`-ветки;
    - быстрая интеграция и обратная связь;
    - подходит для Continuous Deployment;
    - каждый pull request — точка контроля и прозрачности.
- Недостатки:
    - требуется высокий уровень дисциплины: `main` всегда должна быть стабильной;
    - менее удобно при длительной работе над крупными задачами;
    - нет явной поддержки релизных фаз — всё ориентировано на непрерывную поставку.
- GitHub Flow особенно хорошо работает в стартапах, небольших командах, open source проектах, а также в зрелых DevOps-практиках, где важна скорость и прозрачность.

- ### GitLab Flow
- GitLab Flow стал попыткой объединить формальность Git Flow с гибкостью GitHub Flow и адаптировать это под реальные бизнес-процессы. В отличие от других стратегий, он делает акцент не только на ветках кода, но и на способе доставки ценности в разные среды: стейдж, продакшн и так далее.
- Главная идея GitLab Flow — связать ветки разработки с окружениями и бизнес-контекстом. Это достигается за счёт использования так называемых environment branch или release branch, которые соответствуют средам, а также issue-based ветвления, где каждая задача — это отдельная ветка.
- GitLab предлагает три стиля, которые можно комбинировать:
    1. Production branch — одна основная ветка (`main`), релизы деплоятся напрямую оттуда, как в GitHub Flow.
    2. Environment branch — ветки вроде `staging`, `preprod`, `production`, куда вливаются фичи перед выкладкой.
    3. Release branch — отдельные ветки для каждого релиза, как в Git Flow.
- Выбор варианта зависит от зрелости команды, CI/CD-инфраструктуры и процесса QA.
- Пример сценария:
- Задача создаётся в issue-трекере GitLab и автоматически порождает ветку `issue/123-login-fix`. Разработка ведётся в этой ветке, создаётся merge request. После ревью и прохождения CI, ветка вливается, например, в `staging`. Оттуда через пайплайн можно вручную или автоматически продвигать изменения в `production`.
- Преимущества:
    - гибкий: можно адаптировать под процессы конкретной команды;
    - хорошо интегрируется с пайплайнами GitLab CI и автоматическим развёртыванием;
    - возможность настраивать политики доступа и ревью на уровне окружений.
- Недостатки:
    - требует договорённости в команде — важно чётко описать роли веток и правила, когда и куда мёржить изменения;
    - без культуры прозрачности и дисциплины легко запутаться в окружениях.
- GitLab Flow — не жёсткая модель, а скорее набор практик, которые помогают связать задачи, код и доставку. Это особенно важно в DevOps-контексте, где цель — не просто писать код, а поставлять ценность надёжно и предсказуемо.

- ### Какую стратегию выбрать?
- Все стратегии рабочие — важно понять, где какая уместнее. Ниже несколько ориентиров для выбора:
    1. Размер и зрелость команды. Маленькая команда (до 5 человек): GitHub Flow будет оптимальным за счёт простоты и скорости. Средняя команда (5–20 человек): GitLab Flow даёт нужную гибкость без избытка. Большие команды (20+): Git Flow даёт управляемость, особенно если релизы редкие и важна стабильность.
    2. Частота релизов. Ежедневно или чаще: GitHub Flow или GitLab Flow с автоматическим деплоем. Раз в неделю или реже: GitLab Flow или Git Flow.
    3. Архитектура проекта. Монолит: любой подход подойдёт, вопрос в дисциплине. Микросервисы: часто используют GitHub Flow или GitLab Flow — каждая команда может адаптировать стратегию под свой сервис.
    4. Наличие среды CI/CD. Есть полноценный CI/CD: GitHub Flow и GitLab Flow раскрываются полностью. Нет CI/CD: Git Flow проще контролировать вручную, но появляется бюрократия.
    5. Необходимость управления релизами и поддержкой старых версий. Если нужно поддерживать несколько параллельных релизов (например, разные версии для клиентов), Git Flow всё ещё остаётся одним из немногих удобных решений.
    6. Командная культура и зрелость. GitHub Flow требует зрелости: тестов, контроля качества, CI. Без этого он может превратиться в хаос. Git Flow навязывает структуру — меньше свободы, но больше предсказуемости. GitLab Flow даёт баланс — его можно настроить под команду и продукт.
- Важно не только выбрать стратегию, но и договориться всей командой, что она означает на практике. Наличие pull request — это ещё не стратегия. Стратегия — это общий ритм работы, единый язык и предсказуемость, которая освобождает, а не ограничивает.
- ## Trunk-based development: когда хочется быстрее и проще
- Все рассмотренные выше стратегии (Git Flow, GitHub Flow, GitLab Flow) можно считать представителями одного семейства. У них общая логика: изолируем изменения, работаем в ветках, сливаем через pull/merge request. Это помогает контролировать изменения, но и создаёт определённую инерцию.
- В быстроразвивающихся проектах, особенно в продуктах с десятками релизов в день, эти стратегии могут не справляться. Ветки живут слишком долго, слияния накапливают конфликты, ревью тормозят поток. Постепенно команде становится сложнее двигаться, и тогда на сцену выходит подход с иной философией — Trunk-Based Development (TBD).
- TBD — это стратегия, при которой все изменения интегрируются как можно быстрее в одну общую ветку (`main` или `trunk`). Здесь нет долгоживущих `feature`-веток. Все работают на одной линии, быстро коммитят, проходят CI, и, если всё в порядке, изменения немедленно вливаются.
- ### Что было не так с Git Flow и его родственниками?
- Долгоживущие ветки отдаляют интеграцию и создают риски конфликтов. Ревью могут быть узким местом, особенно если нет дежурных ревьюеров. Многоступенчатые пайплайны задерживают доставку фич до пользователей. Каждый merge становится потенциальной болевой точкой — особенно под конец релиза.
- TBD придумали как реакцию на это. Его цель — уменьшить время между написанием кода и его попаданием в продакшн. Но добиться этого можно только при очень высокой зрелости процессов: надёжный CI, хорошее покрытие тестами, культура частой и безопасной интеграции.
- Теперь разберёмся, как TBD реализуется на практике: от ежедневных рабочих процессов до инфраструктурных требований.
- ### Как живёт команда с TBD?
- В Trunk-Based Development ключевая идея — интегрировать как можно раньше. Вместо долгой работы в отдельной ветке мы разбиваем фичу на маленькие шаги и несколько раз в день отправляем их в `main`.
- Вместо долгоживущих фич, используются техники вроде:
    - feature toggle — фича в коде есть, но выключена для пользователей;
    - dark deploy — фичу деплоят, но не активируют;
    - branch by abstraction — временная прослойка, позволяющая менять реализацию без влияния на остальной код.
- Поскольку все работают в одной ветке, качество тестов и быстрота CI становятся особенно важными. Если пайплайн падает — все стоят. Поэтому TBD требует высокой надёжности всего окружения: автотестов, инфраструктуры сборки, различных проверок и алертов.
- Плюсы Trunk-Based Development:
    - минимум конфликтов: никто не залипает в ветках, всё синхронизировано;
    - быстрая обратная связь: CI сразу показывает, что сломано;
    - чистота истории: нет лишних merge-коммитов;
    - ритм команды: постоянная интеграция формирует дисциплину;
- Минусы и ограничения:
    - невозможно без CI/CD: всё должно быть автоматизировано;
    - высокая зрелость команды: нужны культура и опыт;
    - фичи не должны ломать продакшн: требуется изоляция через toggle и другие техники скрытия от пользователя фичи;
- TBD хорош там, где релизы — часть постоянного потока. Это не универсальная замена, но при подходящей инфраструктуре и готовой команде создаётся ощущение, что код по-настоящему живёт в проде.

- ### Сравнение стратегий: Git Flow, GitHub Flow, GitLab Flow и Trunk-Based Development
- Принципы работы:
    - Git Flow: чёткая структура, долгоживущие ветки, формальный релизный процесс.
    - GitHub Flow: простота, короткие ветки, быстрое слияние через pull request.
    - GitLab Flow: гибкость, привязка к окружениям, хорошая интеграция с CI/CD.
    - TBD: частые коммиты прямо в `trunk`, минимум ветвления, ставка на автоматизацию и дисциплину.
- Подходит, если:
    - Git Flow: редкие релизы, строгие QA-процессы, необходимость поддержки старых версий.
    - GitHub Flow: быстрые фичи, зрелая культура ревью, частые выкатки.
    - GitLab Flow: много окружений, продуктовые команды с разным ритмом, сильная DevOps-инфраструктура.
    - TBD: максимальная скорость, высокая зрелость команды, CI/CD как норма, минимум ручных операций.
- Что же выбрать?
    - Для начинающих и небольших команд — GitHub Flow: просто и понятно.
    - Для команд с разными продуктами и средами — GitLab Flow: масштабируется и гибко настраивается.
    - Для стабильных корпоративных проектов с долгими циклами — Git Flow.
    - Для зрелых DevOps-команд с хорошим CI/CD — TBD даёт максимальную отдачу.
- Единственно верной стратегии нет. Выбирайте ту, что подходит вашей команде, инфраструктуре и культуре. И главное — договоритесь о ней все вместе. Тогда это будет не просто схема веток, а опора для совместной работы.

- ## Merge и rebase: два пути объединения изменений
- Теперь, когда у нас есть стратегия и понятные имена веток, возникает следующий вопрос: а как эти ветки объединять? Именно тут начинается реальная работа с Git, и именно здесь рождаются конфликты, недоразумения и легендарные истории о потерянных изменениях.
- Git предлагает два способа объединять ветки: merge и rebase. Оба приводят к одному результату — объединению изменений, но делают это разными способами.
- ### Merge: прямолинейно и прозрачно
- Когда мы выполняем merge, Git берёт две ветки и создаёт новый коммит, который объединяет их изменения. История при этом остаётся разветвлённой: все коммиты сохраняются в том виде, в котором они были, с указанием, когда и что было сделано. Это как если вы с коллегой написали по главе книги, а потом просто соединили их в один документ — видно, у кого какая глава, кто что писал и в каком порядке.
- Плюсом тут можно считать прозрачную историю, но есть и минус - при большом количестве merge-коммитов история может становиться шумной и тяжело читаемой.
- Рассмотрим merge на гипотетическом примере:
    1. Создадим репозиторий с файлом:

- .

mkdir demo-repo && cd demo-repo

- .

git checkout feature-a
echo "Feature A" > a.txt
git add . && git commit -m "add A"

git checkout main
git branch feature-b
git checkout feature-b
echo "Feature B" > b.txt
git add . && git commit -m "add B"
```
    ```
    1. Теперь переключимся на main и сделаем в нём коммит — как будто за время работы над фичами в ветках в main тоже появились новые изменения.


- ### Merge Conflict
- Merge conflict возникает, когда разработчик пытается слить две ветки кода, но изменения в них противоречат друг другу. `git` не может автоматически решить, какую версию строк оставить, и помечает конфликтный фрагмент специальными маркерами `<<<<<<<`, `=======` и `>>>>>>>`, останавливая слияние. Чтобы разрешить конфликт, инженер должен вручную выбрать нужный код, отредактировать его или скомбинировать оба варианта, а затем зафиксировать результат.
- Пример: в основной ветке `main` разработчик изменил логику расчёта итоговой цены в корзине интернет-магазина, заменив фиксированную скидку `discount` на новую функцию `calculate_seasonal_discount()`. Тем временем в ветке `feature/free-shipping` в той же строке добавили учёт бесплатной доставки вызовом `apply_free_shipping()`.
- Алгоритм разрешения:
    1. Открыть конфликтный файл `cart.py`.
    2. Найти маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
    3. Выбрать нужный вариант или написать новый.
    4. Удалить маркеры конфликта.
    5. Сохранить файл.
    6. Выполнить `git add cart.py` и `git commit`.
- К нашему примеру алгоритм применяется так. Содержимое файла сразу после неудачного слияния:
- 
- .
    ```
    ```
# ... previous code ...
<<<<<<< HEAD
    total = apply_discount(total, calculate_seasonal_discount())
=======
    total = apply_free_shipping(total)
>>>>>>> feature/free-shipping
    return total
```
    ```
- При объединении кода правильный порядок такой: сначала рассчитать скидку, затем применить бесплатную доставку. Код обоих разработчиков верный, поэтому изменения нужно не выбирать одно вместо другого, а объединить в нужной последовательности.
- После правки файл выглядит так:
- 
- .
    ```
    ```
# ... previous code ...
    total = apply_discount(total, calculate_seasonal_discount())
    total = apply_free_shipping(total)
    return total
```
    ```
- Выполнив команды `git add cart.py` и `git commit -m 'feat(cart): add free shipping'`, разработчик разрешит конфликт и завершит слияние.

- ### Rebase: переписать историю красиво
- Rebase делает так, будто ваша ветка всегда шла от нужной точки. Git «переигрывает» вашу ветку поверх другой, создавая новые коммиты с теми же изменениями, но на другом основании. Это даёт красивую, линейную историю — будто всё происходило последовательно.
- Плюс этого подхода — ровная, аккуратная история. Минус — хеши коммитов меняются, и если ветка уже была опубликована, это может нарушить ожидания других.
- Посмотрим на гипотетическом примере:
    1. Создадим репозиторий с файлом:
- 
- .
    ```
    ```

git init
echo "Hello" > hello.txt
git add . && git commit -m "initial commit"
```
    ```
    1. Создадим две ветки под фичи и добавим в каждую по файлу:
- 
- .
    ```
    ```
git checkout main
git branch feature-a
git checkout feature-a
echo "Feature A" > a.txt
git add . && git commit -m "add A"

git checkout main
git branch feature-b
git checkout feature-b
echo "Feature B" > b.txt
git add . && git commit -m "add B"
```
    ```
    1. Теперь переключимся на `main` и сделаем в него коммит, как будто пока мы разрабатывали фичи в ветках, в `main` уже что-то обновили:
- 
- .
    ```
    ```

git add . && git commit -m "update main.txt"
```
    ```
    1. Фича A готова в ветке. Перед тем как мёржить в `main`, выполняем rebase.
- 
- .
    ```
    ```

git merge feature-a
```
    ```
    1. Теперь то же самое с фичей B:

- ## Как ветвление влияет на процессы разработки
- Мы рассмотрели, как устроены ветки, какие есть стратегии ветвления, как их выбирать и называть, а также как сливать изменения. Всё это — важные технические моменты. Но нужно понимать: стратегия ветвления — это не частный выбор, а решение, которое влияет на весь процесс разработки. Дело не в командах Git, а в рабочем процессе день за днём.
- На первый взгляд, выбор стратегии ветвления кажется технической деталью. Однако на практике он определяет весь ритм разработки, формат взаимодействия в команде и зрелость инженерной культуры. Это отражение того, как команда думает, как принимает решения, как относится к качеству и скорости.
- Когда мы выбираем Git Flow, то принимаем идею формальных стадий. Это удобно для процессов, где нужно много проверок, ручной QA, релизные кандидаты. Но это создаёт инерцию. Ритм становится «релизным»: собрались, заморозили, стабилизировали, выкатили.
- Когда мы используем GitHub Flow — всё быстрее. Команды работают по принципу «напиши — проверь — выложи». Это требует доверия, хороших автотестов и CI. Всё крутится вокруг pull request: он становится точкой координации.
- GitLab Flow — компромисс. Он даёт инструменты, чтобы и не терять темп, и поддерживать разные среды: `staging`, `preprod`, `production`. Отлично подходит для продуктовых команд, которые работают независимо, но всё же нуждаются в контроле.
- Trunk-Based Development — это уже философия и способ сказать: «мы настолько уверены в своих тестах, процессе и людях, что можем выкладываться непрерывно». Он показывает зрелость команды, доверие к себе и автоматизацию на всех уровнях.
- Одна и та же команда, работая по разным стратегиям, чувствует себя по-разному. С Git Flow участники становятся осторожными и формальными. С GitHub Flow — быстрыми, но иногда небрежными. С TBD — собранными, внимательными, но поначалу напряжёнными: как будто идут по канату.
- Стратегию выбирают не «потому что так пишут», а потому что она подходит вашему состоянию. Это договор, который должен помогать, меняться по мере роста и напоминать, что DevOps — это культура, а не набор инструментов. Культура же — то, как мы ветвимся, коммитим, ревьюим и деплоим.
- 
- ## Ключевые мысли
    1. Ветки — это фундамент командной разработки. Они позволяют изолировать изменения, работать параллельно и не мешать друг другу. Без ветвления будет хаос.
    2. Git реализует ветки умно и дёшево. Ветка — это указатель на коммит. В отличие от старых систем вроде SVN, создание ветки в Git — мгновенная и безопасная операция.
    3. Стратегии ветвления — это соглашения внутри команды. Git Flow, GitHub Flow, GitLab Flow и Trunk-Based Development — это не только схемы, но и отражение культуры работы.
    4. Каждая стратегия подходит под определённые условия:
        - Git Flow: формально, надёжно, для редких релизов.
        - GitHub Flow: быстро, просто, для CI/CD и стартапов.
        - GitLab Flow: гибко, масштабируемо, с учётом окружений.
        - TBD: радикально быстро, требует зрелости и автоматизации.
    5. `merge` и `rebase` — два разных пути объединения. У каждого — свои случаи применения:
        - `merge` — прозрачно, безопасно, но «шумно» в истории.
        - `rebase` — чисто, линейно, но требует осторожности.
    6. Стратегия ветвления влияет на процессы. Она определяет ритм работы, зрелость команды, качество поставки.
