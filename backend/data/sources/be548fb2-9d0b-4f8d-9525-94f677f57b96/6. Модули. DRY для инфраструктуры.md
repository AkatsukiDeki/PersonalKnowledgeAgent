
# Модули: DRY для инфраструктуры

В предыдущих уроках мы многое узнали: как писать манифесты Terraform, параметризировать их переменными и условными конструкциями, а затем разобрались, как придерживаться принципа DRY с помощью циклов.

В этом заключительном уроке мы разберём следующий кейс:

Ваша DevOps-команда выросла и теперь отвечает за стандарты инфраструктуры в компании. При этом каждая из десяти команд разработки пишет свой Terraform-код для создания облачных ресурсов, дублируя логику и допуская разные ошибки. Как предоставить им готовый и протестированный код, который можно настроить под свои нужды, скрыв всю сложную логику?

## Постановка проблемы

Как решать поставленную задачу? Десять команд пишут свой код разного качества, и этим кодом нужно как-то централизованно управлять. Копирование манифестов с эталонным кодом для каждой команды не решит проблему: поддержка копий займёт очень много ресурсов. Внесение изменений под каждый уникальный случай для каждой конфигурации также потребует колоссальных усилий.

Есть ещё вариант — предоставить каждой команде шаблон, который параметризируется в зависимости от входных переменных. Каждая команда формирует набор переменных, и на их основе будет формироваться итоговый манифест. В теории звучит валидно, но представьте, что типовая инфраструктура в облаке состоит из следующих ресурсов: ВМ, диски, сети, балансировщики, правила фаервола, облачные базы данных. Под каждый проект нужно порядка шести уникальных ресурсов с разными параметрами, а кому-то — меньше. Соответственно, нужно учесть все случаи: 21 уникальная ситуация, которую нужно описать условными конструкциями. Это займёт очень много сил и времени, и итоговый код будет невозможно поддерживать из-за его сложности.

Для решения этой задачи в Terraform есть концепция модулей.

### Что такое модуль и когда он необходим?

Модуль Terraform можно описать как стандартизированный блок описания инфраструктуры. Его задача — превратить инфраструктурный код в управляемый, предсказуемый и безопасный процесс, подобно функциям в традиционном программировании. Без модулей поддержка сложных сред становится хаотичной и трудоёмкой.

Но когда необходимо описывать и использовать модули, а когда можно обойтись набором циклов `for_each` и переменных?

**Цель использования:**

- Модуль применяется для создания самодостаточных, переиспользуемых блоков кода, которые инкапсулируют логику работы с несколькими связанными ресурсами.
- `for_each` используется для итерации по однотипному массиву данных и создания нескольких экземпляров одного и того же ресурса. Он подходит для задач, где нужно выполнить однотипные операции без необходимости создания сложной логики.

**Уровень абстракции:**

- Модули предоставляют высокий уровень абстракции, скрывая детали реализации и предоставляя простой интерфейс для работы с ресурсами.
- Циклы и условия работают на низком уровне абстракции.

**Переиспользование кода:**

- Модули предназначены для переиспользования в разных проектах или частях проекта. Они позволяют описать логику один раз и применять её многократно.
- `for_each` не предполагает переиспользования логики как таковой: он лишь упрощает создание нескольких экземпляров ресурса.

**Сложность задачи:**

- Если требуется создать сложную инфраструктуру, состоящую из нескольких взаимосвязанных ресурсов, нужно использовать модули.
- Для простых случаев, когда нужно создать несколько экземпляров одного ресурса, достаточно цикла.

**Управление конфигурацией:**

- С модулями вы управляете набором ресурсов через единый интерфейс, что упрощает внесение изменений и поддержку кода.
- При использовании `for_each` вам придётся управлять конфигурацией каждого ресурса в рамках одного блока кода, что усложняет поддержку большого количества ресурсов.

Таким образом, модули отлично решают поставленную задачу: мы можем описать ими набор унифицированных и переиспользуемых блоков кода. В итоге каждая из команд будет использовать нужный набор модулей в своём проекте, собирая из них нужную конфигурацию.

Резюмируем это в виде небольшой таблицы:

|Критерий|Модули|for_each / циклы|
|---|---|---|
|Цель использования|Создание самодостаточных, переиспользуемых блоков кода, инкапсулирующих логику нескольких связанных ресурсов.|Итерация по однотипным данным и создание нескольких экземпляров одного ресурса без сложной логики|
|Уровень абстракции|Высокий|Низкий|
|Переиспользование кода|Переиспользование кода для разных проектов|Нет переиспользования, а лишь упрощение и оптимизация кода|
|Сложность задачи|Для сложных задач из взаимосвязанных ресурсов|Для решения задач создания однотипных ресурсов|
|Управление конфигурацией|Через единый интерфейс|Конфигурация каждого типа ресурсов отдельно|

### Структура модуля и работа с ним

Технически Terraform позволяет использовать любую директорию с `.tf`-файлами как модуль. Однако, чтобы создать по-настоящему переиспользуемый и поддерживаемый модуль, стоит придерживаться стандартной структуры, рекомендованной HashiCorp.

Структура модуля обычно состоит из набора файлов в директории и выглядит так:

```
├── LICENSE
├── README.md
├── main.tf
├── modules/
├── variables.tf
├── outputs.tf  
```

Это общепринятая рекомендация, которой желательно придерживаться для единообразия.

Подробнее про структуру модуля:

- `LICENSE` — информация о лицензии, по которой будет распространяться ваш модуль. Сам Terraform не использует этот файл — это лишь правило хорошего тона.
- `README.md` — документация по использованию модуля. Terraform не использует этот файл, но Terraform Registry и GitHub показывают пользователям информацию о модуле на его основе.
- `main.tf` — основной набор настроек для модуля. Можно создавать и другие файлы конфигурации и называть так, как удобно для текущего модуля.
- `modules/` — подкаталог для подключаемых модулей, которые использует текущий модуль.
- `variables.tf` — значения всех переменных, необходимых для работы модуля. Можно переопределить в других модулях при необходимости.
- `outputs.tf` — определения вывода для вашего модуля. Удобно для передачи информации о частях вашей инфраструктуры, определённых модулем, в другие части конфигурации.

Ещё подробнее про структуру модулей можно почитать [в документации Terraform](https://www.terraform.io/language/modules/develop/structure).э

Модули бывают **корневые** (root) и **дочерние** (child). Корневой модуль — тот, из которого вызываются подключённые дочерние. Дочерние модули можно хранить локально в директории `modules/` или брать из удалённых registry: GitLab, HTTP URL, Terraform Registry.

Вызов дочерних модулей происходит в файле `.tf`. Например:

```
module "tf-yc-instance" {
  source = "./modules/tf-yc-instance"
  
  foo = bar
  foo1 = bar1
} 
```

В примере объявлен блок `module`, где:

- `"tf-yc-instance"` — имя блока
- `source = "./modules/tf-yc-instance"` — расположение модуля. Может быть как локальным, так и удалённым.
- `foo = bar` и `foo1 = bar1` — набор input-переменных, которые будут переданы в манифесты модуля.

Как мы видим, значения из `terraform.tfvars` можно напрямую передавать при вызове модуля. А можно, как раньше, через файл `terraform.tfvars` и блок `variable`. Это придаёт гибкости конфигурации.

Ещё важно отметить, что блоки output-переменных — важное звено для передачи информации между модулями. Например, в нашем манифесте в output-переменной мы выводим список внешних адресов машин. Если вынести этот код в дочерний модуль, информация об адресах вместо вывода на консоль будет передаваться в зону видимости родительского модуля. Обратиться к нему можно конструкцией: `module.<имя дочернего модуля>.<имя output-переменной>`.

Таким способом в Terraform организовано взаимодействие между модулями: родительский модуль передаёт входные данные через input-переменные, а обратно к нему возвращаются output-переменные. Это можно сравнить с функцией в языках программирования, где переменные — это контракт модуля, его API. Input — входные значения, которые нужны для вызова модуля, а output — возвращаемые значения, которые получаются в результате его работы.

Из этого можно сделать вывод, что модули могут выстраиваться в зависимости с помощью параметра `depends_on`. Однако этот способ стоит применять на практике только в крайних и неочевидных случаях. Основной способ выстраивания зависимостей между модулями — передавать значения output-переменных одного модуля во входные input-переменные другого.

## Организация ресурсов и переменных внутри модуля

Из тезисов выше можно сделать логичное заключение: модуль в Terraform должен быть подобен чёрному ящику, у которого есть понятные механизмы взаимодействия:

- Набор зависимостей версий Terraform и провайдера. Без них никак: нам важно понимать, с какой версией Terraform совместим модуль.
- Набор input-переменных. Это входные параметры модуля, влияющие на результат его работы.
- Набор output-переменных. Это выходные значения модуля, которые можно передать в другой модуль, вывести на консоль или в файл.

Однако как организовать ресурсы и переменные внутри нашего «чёрного ящика» — модуля?

### Проблема магических значений

Хорошей практикой считается использование local-переменных как единого места указания значений переменных и условий. Например:

```
resource "yandex_compute_instance" "web" {
  name = "web-server"
  zone = "ru-central1-a"

  boot_disk {
    initialize_params {
      image_id = "fd8ivd16f15f123..."  # что это за ID? Откуда он взят?
      size = 20
    }
  }

  network_interface {
    subnet_id = "e90m5678n90p12345..."  # неясно, какая подсеть
  }
}

resource "yandex_vpc_address" "static_ip" {
  external_ipv4_address {
    zone_id = "ru-central1-a"  # Повторение зоны
  }
} 
```

Пример выше показывает проблему «магических значений»: когда значения переменных жёстко заданы и разбросаны по коду без какого-либо контекста.

Использование local-переменных решает эту проблему:

```
locals {
  # параметры зоны, объявленные в одном месте
  zone = "ru-central1-a"

  # образ ОС
  os_image = {
    name = "ubuntu-2204-lts"
    id   = "fd8ivd16f15f12345abc"
  }

  # описание подсети
  network = {
    subnet_name = "prod-web-subnet"
    subnet_id   = "e90m5678n90p12345def"
  }
} 
```

Используя `locals`, мы в одном месте объявляем и правим все значения, которые используются внутри модуля. В случае повторного использования значения, можно сослаться на уже объявленную local-переменную или изменить её значение в одном месте, чтобы обновление применилось везде.

Такой подход упрощает рефакторинг и расширение кода, избавляет от дублирования и снижает вероятность ошибок.

### Проблема относительности путей

Код Terraform часто работает с файлами на файловой системе, например с ключами, шаблонами и служебными файлами. В связи с этим часто возникает проблема, особенно при использовании дочерних модулей: жёстко заданные пути ломаются.

Для решения этой задачи в Terraform существуют служебные переменные:

- `path.module` — указывает абсолютный путь к директории текущего модуля;
- `path.root` — указывает абсолютный путь к директории корневого модуля, где запущен `terraform init`.
- `path.cwd` — указывает на текущую директорию терминала.

Рассмотрим следующий пример:

```
resource "yandex_compute_instance" "app" {
  name = "app"
  
  metadata = {
    user-data = file("/home/user/projects/my-infra/modules/app/cloud-init.yaml")
  }
} 
```

Какие проблемы сразу бросаются в глаза:

- путь привязан к конкретной машине и расположению проекта;
- при переносе модуля в другую директорию или репозиторий код сломается;
- невозможно повторно использовать модуль в других проектах.

Решение с помощью `${path.module}`:

```
resource "yandex_compute_instance" "app" {
  name = "my-app"
  
  metadata = {
    user-data = file("${path.module}/cloud-init.yaml")
  }
} 
```

Получилось очень лаконично, а главное — проблемы решены. Переменная `path.module` примет новое значение в зависимости от расположения модуля на файловой системе.

Хорошей практикой будет комбинация local-переменных с функцией проверки файла на существование `fileexists()`. Например:

```
locals {
  config_path = fileexists("${path.module}/config.json") ? "${path.module}/config.json" : null 
} 
```

Эта проблема особенно актуальна при интеграции Terraform с CI/CD-пайплайнами, поскольку там среда выполнения кода каждый раз разная и создаётся динамически.


## Практика: выносим код создания ВМ в отдельный модуль

Настало время практики! Оформим наш код создания ВМ в отдельный модуль.

**Что переносим и что остаётся в корне**

- В **дочерний модуль** (`modules/tf-yc-instance/`) переносится логика ВМ: блоки `resource` и при необходимости `data`, которые относятся к созданию инстансов, а также файлы `variables.tf` и `outputs.tf` модуля (итоговое имя файла с выходами — **`outputs.tf`**, не `output.tf`).
- В **корне** проекта остаются блоки **`terraform { ... }`** (в том числе `required_providers`) и **`provider "yandex" { ... }`** — провайдер и версии задаются один раз для всего стека; дочерний модуль по умолчанию использует настройки провайдера родителя.
- Если в манифестах создаётся ресурс, кроме `yandex_compute_instance`, его можно удалить — по условию задания он не нужен.

**Шаги**

1. Создайте каталог `modules/tf-yc-instance/` в проекте.
2. Перенесите в `modules/tf-yc-instance/` файлы с ресурсами ВМ и переменными: `main.tf`, `variables.tf`, `outputs.tf` (переименуйте `output.tf` в `outputs.tf`, если у вас было старое имя). Удалите из перенесённого `main.tf` блоки `terraform` и `provider`, если они там были — они должны остаться только в корне. **Важно:** в корне не оставляйте вторую копию той же логики — удалите или замените старый манифест с ресурсами ВМ, иначе Terraform попытается управлять инстансами и из модуля, и из корня.
3. В **корне** оставьте один `main.tf` (или разнесите по файлам), где есть `terraform`, `provider "yandex"` и **вызов модуля** вместо бывших ресурсов ВМ. Пример ниже показывает часть аргументов; **остальные входы модуля должны совпадать с объявлениями в `variables.tf` дочернего модуля** (сеть, образ, зона и т.д., если они у вас были в коде до рефакторинга). Их можно задавать в блоке `module` теми же значениями, что раньше, либо передавать из корня через `var.*` и при необходимости `terraform.tfvars`.

```
module "tf-yc-instance" {
  source = "./modules/tf-yc-instance"
  name = "lesson-terraform-dm-vm"
  vm_size = {
    memory = 4
    cores  = 2
  }
  vm_names = ["front", "back", "db"]
} 
```

4. В корне создайте или дополните **`outputs.tf`**: пробросьте выход дочернего модуля. Если прежний `output` остался в `main.tf`, перенесите его сюда или удалите дубликат.

```
output "root_external_ips" {
  description = "Public IPs from child module"
  value       = module.tf-yc-instance.external_ips
} 
```

5. Выполните **`terraform init`** (обязательно после появления блока `module` или смены пути к модулю), затем `terraform plan` и **`terraform apply`**. После успешного `apply` проверьте, что в выводе есть ожидаемые IP. **Как читать план:** при первом развёртывании или после `terraform destroy` вы увидите создание ресурсов модуля. Если те же ВМ уже существовали в state как ресурсы **корневого** модуля, а вы перенесли код в дочерний модуль, план часто покажет удаление старых ресурсов и создание новых — это ожидаемо из‑за смены адресов в state, а не признак ошибки в шагах; чтобы не пересоздавать инстансы, в сложных случаях используют блоки `moved` или `terraform state mv` (выходят за рамки базовой практики).
6. После проверки удалите ресурсы:

```
terraform destroy 
```

**Ожидаемая структура каталогов** (файлы вроде `terraform.tfvars`, `README.md` или `versions.tf` в корне могут остаться из прошлых уроков — это нормально)

```
├── main.tf
├── modules
│   └── tf-yc-instance
│       ├── main.tf
│       ├── outputs.tf
│       └── variables.tf
├── outputs.tf 
```

Как работают модули мы выяснили. Осталось разобраться, как организовать их хранение в удалённых ресурсах.

### Хранение модулей и организация доступа

Хранение модулей в локальных директориях устроено просто и понятно, но не решает поставленную нами задачу: «Как организовать доступ к модулям для множества команд?». Если каждая команда будет копировать исходники модуля себе, мы не достигнем цели простой и понятной организации доступа. А что делать, если модуль обновился и части команд нужна старая версия, а части — новая?

Terraform поддерживает удалённые источники для хранения модулей. Хранилищем могут выступать как специализированные реестры (в том числе от Hashicorp), так и публичные Git-репозитории.

Например, можно ознакомиться с модулями от Яндекс Облака, которые расположены в [публичном GitHub-репозитории](https://github.com/terraform-yc-modules).

Обратите внимание на подробный README. В нём описаны зависимости, input- и output-переменные.

Вызвать модуль напрямую из Git можно так:

```
module "compute_instance" {
  source = "git::https://github.com/terraform-yc-modules/terraform-yc-compute-instance.git?ref=v1.0.3"

  image_family              = "image"
  zone                      = "ru-central1-a"
  name                      = "name"
  ... опустим остальную конфигурацию ...
} 
```

Версию модуля удобно привязать к Git-тегу, а формируется она обычным [SemVer](https://semver.org/lang/ru/).

Системы хранения версий кода могут также хранить модули не как исходный код, а как пакет, понимая, что это модуль Terraform — например, в [GitLab](https://praktikum.gitlab.yandexcloud.net/help/user/packages/terraform_module_registry/index). Это даёт больше гибкости в управлении пакетами, в частности, избавляет от необходимости привязки публикации модуля к Git.

При использовании специализированного репозитория Terraform вызов модуля выглядит, например, так:

```
module "compute_instance" {
  source  = "terraform-yacloud-modules/instance/yandex"
  version = "2.17.0"
  
  ... опустим остальную конфигурацию ...
} 
```

Поле `version` указывает нужную версию модуля в репозитории. Оно поддерживает оператор `~>`, который позволяет обновлять минорные версии, например:

```
version = "~> 1.0" 
```

Или операторы сравнений: `<`, `>`, `=`. Например:

```
version = ">= 1.0", "< 2.0" 
```

Задаёт явный диапазон, аналогичный `"~> 1.0"`.

Чтобы обновить версию модуля локально, можно воспользоватся командой:

```
terraform init -upgrade 
```

При работе с модулями не стоит всегда полагаться на последнюю версию, особенно если модуль разрабатывает внешняя (а иногда и незнакомая вам) команда. Хорошей практикой будет поэтапное обновление версии модуля: сначала проверка на тестовых окружениях, потом перенос изменений на прод. Подход IaC позволит быстро откатить изменения на любом стенде в случае непредвиденной ситуации.

Минорные версии часто обновляются автоматически, поскольку они не содержат изменений логики, а включают багфиксы. Поэтому распространённый подход к обновлению инфраструктурного кода выглядит так:

- `prod` — явное указание версии.

```
version = "1.2.3" 
```

- `preprod\stage` — явное тестирование версии, которая пойдёт в прод.

```
version = "1.2.3" 
```

- `dev\test` — тестирование целевой версии; часто минорные патчи обновляются автоматически.

```
version = "~> 1.5" 
```

Важно понимать, что это лишь один из подходов и он не претендует на абсолютную истину. Итоговая политика обновлений — компромисс между лучшими практиками, удобством реализации и бизнес-требованиями.

Про удалённое хранение модулей можно почитать [в документации](https://developer.hashicorp.com/terraform/language/modules/sources).


## Практика: настроим хранение модуля в GitLab

- Подготовьте [репозиторий](https://praktikum.gitlab.yandexcloud.net/), с которым работали весь спринт. Модули будут храниться в разделе `Operate` => `Terraform modules`

![Раздел Operate — Terraform modules в репозитории GitLab](https://pictures.s3.yandex.net/resources/3-5-1_1765821380.png)

- Нужно организовать доступ к репозиторию. Сделаем это с помощью [токена репозитория](https://praktikum.gitlab.yandexcloud.net/help/user/project/deploy_tokens/index.md). Он привязан к репозиторию и отлично подойдёт под нашу задачу.
    
- Перейдите в `Settings` => `Access Token`
    

![Настройки Settings — Access Token в GitLab](https://pictures.s3.yandex.net/resources/3-5-2_1765821400.png)

Role: Developer

Права: api, write_repository

- Сохраните себе токен.
- Сформируйте архив для публикации модуля командой:

```
tar -czf tf-yc-instance.tgz modules/tf-yc-instance 
```

- Можно отправлять:

```
curl --fail-with-body --header "PRIVATE-TOKEN: <ВАШ ТОКЕН>" \
     --upload-file tf-yc-instance.tgz \
     "https://praktikum.gitlab.yandexcloud.net/api/v4/projects/<ID ПРОЕКТА>/packages/terraform/modules/my-modules/tf-yc-instance-<ТВОЙ STD-ID>/0.0.1/file" 
```

Обратите внимание, что в GitLab значения в URL: `tf-yc-instance-<ТВОЙ STD-ID>/` должны быть уникальными. Поэтому, чтобы запрос выполнился и не было путаницы, нужно вписать свой уникальный логин студента в путь.

Токен уже есть, ID проекта можно узнать в `Settings` => `General` => `Project ID`

![Project ID в Settings — General репозитория GitLab](https://pictures.s3.yandex.net/resources/3-5-3_1765821417.png)

Сообщение вида:

```
{"message":"201 Created"} 
```

Говорит о том, что всё получилось.

**Чеклист для самопроверки:**

1. Команда `curl` вернула статус `201`.
2. Модуль появился в разделе `Terraform modules` репозитория.

Вы получили хранилище пакетов, где их удобно версионировать, управлять доступом с помощью экосистемы GitLab и фиксировать историю изменений.
