
Lean-принципы, пришедшие из бережливого производства, направлены на устранение потерь и непрерывное улучшение процессов. В контексте CI-конвейеров это отказ от «муды» (лишних действий и задержек), чтобы конвейер работал быстрее и надёжнее.

Lean-подход в CI — это минимум простоев и лишних шагов, маленькие порции кода и быстрый фидбэк. Ошибки нужно ловить как можно раньше: автоматические тесты и проверки стоит встраивать в начало конвейера, а каждый этап должен приносить понятную пользу и не дублировать другие.

В этом уроке мы разберём типичные ошибки (антипаттерны) при реализации CI-конвейеров и посмотрим, как их исправлять c помощью lean-принципов. Примеры будем разбирать на GitLab CI.

## Антипаттерн №1: монолитный этап (все действия в одном шаге конвейера)

Один из самых распространённых антипаттернов при настройке CI — попытка упаковать все задачи конвейера в одну (джоб). Новички часто пишут в `.gitlab-ci.yml` один длинный скрипт, который устанавливает зависимости, собирает проект, запускает линтер, прогоняет юнит-тесты, строит Docker-образ, пушит его в реестр, а иногда сразу и деплоит.

Пример:

```YAML
ci_all_in_one:
  stage: build
  script:
    - npm ci
    - npm run lint
    - npm run test
    - docker build -t myapp .
    - docker push myapp
    - ssh prod 'docker pull myapp && docker restart app' 
```

На первый взгляд удобно — всё в одном месте. Но такой подход приводит к ряду серьёзных проблем:

- **Нет прозрачности процесса.** При запуске такой задачи непонятно, на каком именно этапе сейчас находится сборка. Если в CI-интерфейсе видно только `ci_all_in_one` в статусе `Running`, остаётся только гадать, что происходит: идёт lint, выполняются тесты или уже пушится образ.
- **Неочевидно, где упало.** Если задача завершилась с ошибкой, в логах придётся искать, какой шаг сломался. Иногда на больших проектах логи могут занимать тысячи строк, и поиск причины превращается в долгий разбор завала.
- **Нет параллельного выполнения.** GitLab CI может запускать независимые задачи параллельно, сокращая общее время конвейера. Но если всё в одной задаче — никакого параллелизма не будет. Даже линтер и юнит-тесты, которые можно было бы прогнать одновременно, выполняются один за другим.
- **Затруднённый перезапуск.** Если линтер временно сломался или тест упал временного сбоя инфраструктуры, придётся перезапускать всю задачу — со сборкой и деплоем, даже если ранее они прошли без ошибок.

Кроме того, такой пайплайн плохо сочетается с принципом Fail Fast: ошибки находятся поздно, а даже мелкая проблема заставляет прогонять слишком большой кусок конвейера целиком.

### Как это исправить

1. Разбиваем на этапы (`stages`) и отдельные задачи (`jobs`).

GitLab CI позволяет явно задать последовательность этапов (stages). Например:

```YAML
stages:
  - lint
  - test
  - build
  - deploy 
```

Затем каждую задачу описываем как отдельную в соответствующем этапе:

```YAML
lint:
  stage: lint
  script:
    - npm run lint

unit_test:
  stage: test
  script:
    - npm run test

docker_build:
  stage: build
  script:
    - docker build -t myapp .

deploy_prod:
  stage: deploy
  script:
    - docker push myapp
    - ssh prod 'docker pull myapp && docker restart app' 
```

Такой конвейер даёт массу преимуществ:

- **Прозрачность:** в интерфейсе CI видно стадии (`lint` → `test` → `build` → `deploy`) и прогресс по ним.
- **Локализация ошибок:** если упал `unit_test`, сразу понятно, что причина в тестах.
- **Параллельность:** если у вас есть несколько разных тестов (например, линтер, юнит-тесты и интеграционные тесты), их можно запускать одновременно, сокращая общее время.
- **Гибкий перезапуск:** если линтер временно упал — можно перезапустить только эту задачу, не трогая `build` и `deploy`.
    
- Используем `needs` для параллелизма и оптимальной зависимости.
    

GitLab CI поддерживает не только последовательные этапы, но и графы зависимостей через `needs`. Это позволяет параллельно запускать линтеры и юнит-тесты сразу после установки зависимостей.

```YAML
stages:
  - prepare
  - checks
  - build
  - deploy

install:
  stage: prepare
  script:
    - npm ci
  artifacts:
    paths:
      - node_modules/

lint:
  stage: checks
  needs: ["install"]
  script:
    - npm run lint

test:
  stage: checks
  needs: ["install"]
  script:
    - npm run test

docker_build:
  stage: build
  needs: ["test", "lint"]
  script:
    - docker build -t myapp . 
```

### Вывод

Антипаттерн «все действия в одном шаге» снижает прозрачность, замедляет разработку, мешает быстро находить ошибки и усложняет сопровождение.

Лучше следовать lean-принципам и строить CI так, чтобы:

- каждая задача занималась одним конкретным действием,
- конвейер показывал чёткие стадии,
- ошибки выявлялись как можно раньше.

При этом не стоит впадать в крайность и создавать десятки крошечных задач. Лучше ориентироваться на смысловые блоки (lint, тесты, сборка образа, деплой) — это и читаемо, и управляемо.

## Антипаттерн №2: дублирование этапов и шагов (повторяющийся код конвейера)

Дублирование в CI-конвейере — это ситуация, когда в `.gitlab-ci.yml` повторяются одни и те же фрагменты кода, только с незначительными изменениями. Чаще всего это выглядит так:

- одинаковые скрипты, скопированные с небольшими отличиями, запускаются в разных окружениях (`dev`, `staging`, `prod`);
- несколько задач содержат один и тот же `script`, `before_script` или `rules`;
- настройка переменных, кеша или артефактов дублируется.

Пример проблемного кода:

```YAML
build-dev:
  stage: build
  script:
    - ./build.sh
  rules:
    - changes: ["dev/**/*"]

build-qa:
  stage: build
  script:
    - ./build.sh
  rules:
    - changes: ["qa/**/*"]

build-prod:
  stage: build
  script:
    - ./build.sh
  rules:
    - changes: ["prod/**/*"] 
```

Вроде бы проблема небольшая, но чем больше проект, тем сильнее последствия:

- **Трудно вносить изменения.** Если нужно изменить процесс сборки (например, поменять команду `./build.sh` на `./ci/build.sh`), придётся делать это в нескольких местах — есть риск что-то пропустить. Такая поддержка становится утомительной и ведёт к ошибкам.
- **Нарушение принципа DRY.** В разработке действует принцип Don’t Repeat Yourself (DRY): один источник правды для каждой части логики. Дублируя код в CI, вы нарушаете этот принцип и усложняете сопровождение.
- **Риск рассинхронизации.** Через пару месяцев одну задачу могут поправить, а другие забудут. В результате сборка в разных окружениях начнёт работать по-разному, а выявить это будет сложно.
- **Читать CI-конфигурации становится сложно.** Большой `.gitlab-ci.yml` с копипастой хуже читается и медленнее анализируется разработчиками. Это увеличивает время на ревью и диагностику.

### Как это исправить

1. Используем шаблоны задач и `extends`.

GitLab CI предоставляет мощный механизм, чтобы устранить дублирование: скрытые задачи-шаблоны. Такие задачи начинаются с точки (например, `.build_template`). Они не запускаются сами, но предназначаются для наследования через `extends`.

Пример:

```YAML
.build_template:
  stage: build
  script:
    - ./build.sh

.dev_rules:
  rules:
    - changes: ["dev/**/*"]

.qa_rules:
  rules:
    - changes: ["qa/**/*"]

.prod_rules:
  rules:
    - changes: ["prod/**/*"] 
```

Затем конкретные задачи можно строить на основе этих шаблонов:

```YAML
build-dev:
  extends:
    - .build_template
    - .dev_rules

build-qa:
  extends:
    - .build_template
    - .qa_rules

build-prod:
  extends:
    - .build_template
    - .prod_rules 
```

2. Используем YAML anchors (якоря).

Если файл GitLab CI короткий и не хочется вводить много `extends`, можно воспользоваться якорями YAML. Например:

```YAML
.build_step: &build_step
  stage: build
  script:
    - ./build.sh

build-dev:
  <<: *build_step
  rules:
    - changes: ["dev/**/*"]

build-qa:
  <<: *build_step
  rules:
    - changes: ["qa/**/*"] 
```

Якоря работают прямо на уровне YAML. Они копируют структуру, но часто делают конфигурацию менее читаемой. Для крупных пайплайнов `extends` предпочтительнее.

3. Централизация переменных и кеша.

Часто дублируются не только скрипты, но и `cache`, `before_script` или глобальные переменные. Их можно вынести в верхнюю часть файла:

```YAML
default:
  before_script:
    - echo "Starting build"
  cache:
    key: "$CI_PROJECT_NAME"
    paths:
      - node_modules/ 
```

Тогда все задачи автоматически будут наследовать эти настройки.

### Вывод

Избавляться от дублирования важно, но превращать `.gitlab-ci.yml` в абстрактный «фреймворк», который понимает только автор, нельзя. Иногда небольшое повторение оправдано, если оно упрощает чтение конвейера. Главная цель — не размазывать логику по десяткам мест и не править полфайла ради одного изменения в процессе.

Антипаттерн с дублированием шагов в CI — это ловушка, в которую легко попасть на старте. Он замедляет развитие проекта, повышает риск ошибок и увеличивает стоимость поддержки.

GitLab CI даёт все инструменты, чтобы этого избежать: `extends`, скрытые шаблоны, якоря и глобальные секции (`default`). Используйте их, чтобы ваш конвейер оставался компактным, поддерживаемым и отвечал lean-принципам — без лишней работы и без повторов.

## Антипаттерн №3: избыточные действия в конвейере (лишние или повторные шаги)

Мы уже говорили в предыдущих уроках про `artifacts` и `cache`, но здесь важно ещё раз коротко напомнить разницу между ними — именно она помогает убрать лишние действия из пайплайна.

`artifacts` — это способ передать результаты одного job следующему. Без них каждый job, которому нужен скомпилированный файл или собранный пакет, вынужден пересобирать его с нуля. Повторная сборка — это прямые потери: время раннера, трафик, задержка обратной связи.

`cache` — это способ сохранить зависимости (`node_modules/`, `.m2/`, `venv/`) между пайплайнами одной ветки. Без кеша каждый job устанавливает все зависимости заново, даже если `package-lock.json` не менялся. Для проекта с сотнями зависимостей это легко превращается в 2–3 лишних минуты на каждый пуш.

Антипаттерн с избыточными действиями проявляется, когда в CI-конвейере выполняются действия, которые не добавляют никакой ценности для конечного результата, повторяются без необходимости и могли бы выполняться реже или в другом месте.

Типичные примеры:

- каждая задача по новой скачивает зависимости;
- проект повторно собирается несколько раз в разных джобах;
- тяжёлые тесты или сканеры безопасности запускаются на каждый коммит, даже если меняется только README;
- конвейер генерирует артефакты, которые потом нигде не используются.

Почему это плохо:

- **Удлиняет время конвейера.** Повторная сборка, скачивание зависимостей или запуск одинаковых тестов в разных местах увеличивает общее время прохождения конвейера.
- **Перегружает CI-инфраструктуру.** GitLab тратит процессорное время, сеть и диски на ненужные действия. Много параллельных пайплайнов приводят к узким местам.
- **Приводит к избыточным расходам.** При использовании SaaS CI с оплатой за минуты (или за ресурсы), лишние шаги прямо увеличивают счета за CI/CD.
- **Усложняет сопровождение.** Чем больше в конвейере бесполезных шагов и скриптов, тем сложнее его читать, понимать и поддерживать.

### Как это исправить

1. Использовать артефакты для передачи результатов.

Если проект уже собран, не нужно повторно собирать его в другом джобе для тестов или деплоя.

```YAML
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/

unit_test:
  stage: test
  dependencies:
    - build
  script:
    - npm test 
```

Здесь `unit_test` использует файлы из `dist/`, сгенерированные на этапе `build`, не пересобирая их.

2. Кешировать зависимости.

Если каждая задача скачивает `node_modules` или пакеты Maven с нуля, время и трафик тратятся впустую.

```YAML
cache:
  key: "$CI_PROJECT_NAME"
  paths:
    - node_modules/

install:
  stage: prepare
  script:
    - npm ci 
```

В следующий раз `npm ci` возьмёт зависимости из кеша, ускоряя процесс.

3. Запускать тяжёлые задачи только при необходимости.

Например, `security scan` или `e2e`-тесты можно запускать не на каждый коммит, а только при мёрже в `develop` или `main`.

```YAML
e2e_tests:
  script: ./run_e2e.sh
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"' 
```

4. Избегать дублирования тестов.

Иногда юнит-тесты и интеграционные тесты проверяют одно и то же. Проанализируйте набор тестов и сократите перекрытия.

### Вывод

Lean-принципы учат устранять всё, что не добавляет ценности конечному продукту. Каждый шаг в CI должен проверять или доставлять качество. Если он этого не делает, то его лучше убрать, перенести или сократить.

Избыточные действия в CI — скрытая угроза скорости и стабильности. Они незаметно замедляют конвейер, перегружают инфраструктуру и демотивируют команду, которая начинает ждать результатов всё дольше. Использование артефактов, кешей и умных правил запуска позволит сделать конвейер более «бережливым» (lean): быстрее, дешевле и эффективнее.

Избыточные действия в пайплайне — это не только повторная сборка и лишние запуски тестов, но и отсутствие кеширования зависимостей. Разберём это на отдельном практическом примере.

## Практическое задание 1

Пайплайн без кеширования зависимостей на первый взгляд кажется рабочим: задачи запускаются, проверки выполняются, ошибок нет. Но при каждом новом запуске CI заново скачивает те же самые зависимости — даже если они не изменились.

Это создаёт лишние потери:

- увеличивается время выполнения конвейера;
- растёт нагрузка на раннеры, сеть и пакетные репозитории;
- обратная связь приходит позже;
- CI/CD-ресурсы расходуются неэффективно.

Пример проблемной конфигурации:

```YAML
stages:
  - lint
  - test

lint_job:
  stage: lint
  script:
    - npm ci
    - npm run lint

test_job:
  stage: test
  script:
    - npm ci
    - npm run test 
```

Здесь и `lint_job`, и `test_job` по отдельности выполняют `npm ci`. В результате зависимости скачиваются повторно, хотя могли бы переиспользоваться через кеш.


> Случай
> Какие изменения помогут исправить антипаттерн «пайплайн без кеширования»? Выберите все правильные варианты.

- **Добавить `cache:` для зависимостей.**
*Это позволит переиспользовать уже скачанные пакеты между задачами и пайплайнами.*

- **Использовать ключ кеша (например, `$CI_COMMIT_REF_SLUG`).**
*Это помогает разделять кеши по веткам и снижает риск конфликтов.*

- **Вынести настройки кеша в `default:`.**
*Это уменьшает дублирование и делает конфигурацию чище.*


Пример решения

```YAML
stages:
  - lint
  - test

default:
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths:
      - node_modules/

lint_job:
  stage: lint
  script:
    - npm ci
    - npm run lint

test_job:
  stage: test
  script:
    - npm ci
    - npm run test 
```

Чем этот вариант лучше исходного:

- зависимости могут переиспользоваться между задачами и следующими пайплайнами;
- уменьшается время выполнения `lint` и `test`;
- снижается нагрузка на сеть и пакетный реестр;
- конвейер становится ближе к lean-подходу — без лишних повторных действий.

## Антипаттерн №4: запоздалый или некачественный репортинг (обратная связь конвейера)

Один из скрытых, но очень опасных антипаттернов в CI — когда обратная связь приходит слишком поздно или в неудобной, неясной форме. Проще говоря, конвейер сообщает о проблемах только в самом конце или формулирует их так, что разработчику трудно понять, что именно сломалось.

Примеры таких сценариев:

- Конвейер сначала выполняет сборку и упаковку артефактов, а только потом запускает линтеры или юнит-тесты.
- Нет механизма fail fast — конвейер продолжает выполнять следующие шаги даже после провала критичной проверки.
- Тесты выполняются, но результаты никак не оформляются в отчёты — приходится лезть в длинные логи и искать упавшие тесты вручную.
- Нет уведомлений (на почту, в Slack или по другим каналам).
- Не используются визуальные отчёты покрытия, сканеры безопасности и анализ качества.

Во всех случаях проблема одна: команда узнаёт об ошибке слишком поздно или в неудобном виде — и тратит время на её поиск там, где уже нужно исправлять.

Почему это плохо:

- **Увеличивает время реакции на ошибки.** Ошибки в коде выявляются только в конце, команда теряет время на ненужные шаги и получает обратную связь слишком поздно.
- **Приводит к росту затрат.** CI расходует ресурсы на сборку, деплой и тесты, которые изначально были обречены из-за бага — в итоге тратится процессорное время раннеров и трафик.
- **Демотивирует разработчиков.** Если CI сообщает о проблеме спустя 20–30 минут, теряется темп. Разработчик вынужден переключаться на другие задачи, а потом возвращаться и вспоминать контекст.
- **Усложняет анализ.** Если результаты тестов выводятся только в логах, приходится тратить время на ручной поиск упавших тестов и их причин.

### Как это исправить

1. Переносим проверки влево (shift left).

Линтеры и юнит-тесты запускайте в самом начале конвейера, а не после сборки образов.

```YAML
stages:
  - lint
  - test
  - build
  - deploy

lint:
  stage: lint
  script:
    - npm run lint

unit_test:
  stage: test
  script:
    - npm test 
```

Если `npm run lint` не прошёл, конвейер завершится сразу.

2. Используем fail fast.

Не подавляйте ошибки через `|| true`. Убедитесь, что критичные проверки действительно прерывают конвейер.

3. Генерируем отчёты.

Используйте встроенные отчёты GitLab для тестов и покрытия.

```YAML
unit_test:
  stage: test
  script:
    - npm test -- --reporters=jest-junit
  artifacts:
    reports:
      junit: junit.xml
coverage: '/\d+%/' 
```

Благодаря этому упавшие тесты будут видны прямо в интерфейсе Merge Request.

4. Настраиваем уведомления.

Добавьте уведомления в Slack или по email.

```YAML
notify:
  stage: notify
  script:
    - curl -X POST -H 'Content-type: application/json' --data '{"text":"Pipeline $CI_PIPELINE_ID completed"}' https://hooks.slack.com/services/...
  when: always 
```

5. Мониторим конвейер.

Регулярно смотрите, сколько времени занимают lint и тесты. Если они в конце или идут слишком долго — перестраивайте.

### Вывод

Lean-принципы подчёркивают важность быстрой обратной связи. Цель проста: чтобы CI за несколько минут сказал либо «всё окей, можно двигаться дальше», либо «есть проблема, исправь её срочно».

Запоздалый или некачественный репортинг — антипаттерн, который не всегда заметен в коде .gitlab-ci.yml, но сильно замедляет разработку. Стройте конвейер так, чтобы ошибки всплывали как можно раньше, результаты были наглядны, а уведомления приходили автоматически. Это экономит время, ресурсы и нервы команды.

![[Pasted image 20260805164359.png]]

> Иногда тесты идут до сборки, а иногда — после.
> Порядок `lint → test → build` работает, когда тесты не требуют скомпилированных артефактов — например, в Python или Node.js без отдельного шага сборки. В этих языках можно запустить `pytest` или `jest` прямо по исходникам.

Для компилируемых языков (Java, Go, C#) тесты запускаются **после** сборки: без `.class`-файлов или бинарников тест просто не запустится. Там правильный порядок — `lint → build → test`.

Оба варианта верны. Выбор зависит от стека: если ваши тесты требуют собранного артефакта — тесты идут после сборки; если нет — тесты можно вынести вперёд для более раннего фидбека.

## Антипаттерн №5: неконтролируемое время выполнения конвейера (медленный CI)

Ещё один распространённый антипаттерн в CI — ситуация, когда конвейер работает слишком долго (20, 30, 40 минут и больше), за этим никто не следит, а время выполнения продолжает расти с каждой итерацией. Команда уже привыкла к тому, что «CI идёт долго», и даже не пытается это улучшить. В итоге:

- **Замедляется цикл разработки.** Если конвейер работает больше 30 минут, разработчики остаются без быстрой обратной связи. В итоге они переключаются на другие задачи, теряют фокус, и исправления начинают затягиваться.
- **Увеличивается стоимость.** Медленный CI использует больше ресурсов GitLab. При платном SaaS это прямо влияет на расходы.
- **Появляется соблазн мёржить без ожидания.** Когда команда устаёт ждать, появляются обходные решения вроде: «Замёржу сейчас, а пайплайн пусть потом докрутится». Это подрывает культуру качества.

### Как это исправить

1. Замеряем и ставим цели.

Разбейте конвейер по стадиям и измерьте время:

- подготовка (install),
- линт,
- юнит-тесты,
- интеграционные тесты,
- сборка образа,
- деплой.

Задайте себе цель. Например: «полное прохождение CI-конвейера меньше 10 минут».

Это не жёсткий универсальный стандарт, а ориентир: чем быстрее команда получает результат, тем выше шанс, что разработчик сразу исправит проблему, не теряя контекст.

2. Параллелизация.

Убедитесь, что задачи, которые могут выполняться одновременно, действительно запускаются параллельно.

```YAML
lint:
  stage: checks
  script: npm run lint

unit_tests:
  stage: checks
  script: npm test

integration_tests:
  stage: checks
  script: npm run integration 
```

Все три задачи стартуют одновременно!

3. Оптимизация тестов:
    
4. разбейте тесты на группы и запускайте в отдельных джобах,
5. используйте маркировку (`fast`/`slow`) и запускайте медленные только, например, на `merge`,
6. удалите дубликаты и flaky-тесты.
    
7. Используйте кеш и артефакты.
    

Чтобы не скачивать зависимости заново, используйте `cache`. Для передачи сборок — `artifacts`.

```YAML
cache:
  key: "$CI_PROJECT_NAME"
  paths:
    - node_modules/ 
```

5. Следите за инфраструктурой.

Если ресурсы в Gitlab сильно ограничены, то конвейеры будут ждать в очереди. Решение:

- добавить ресурсов,
- использовать более мощные машины,
- включить автомасштабирование.
    
- Используйте `timeout`.
    

Не позволяйте задаче висеть бесконечно.

```YAML
integration_tests:
  script: npm run integration
  timeout: 15m 
```

### Вывод

Lean-принципы требуют постоянной оптимизации. Раз в спринт или месяц анализируйте CI и улучшайте его.

Медленный CI — это скрытый враг продуктивности. Он отнимает время у команды, повышает затраты и замедляет доставку ценности пользователям.

Следите за временем выполнения, используйте параллельный запуск, кеш и артефакты — тогда CI будет помогать команде, а не тормозить её.

## Антипаттерн №6: нестабильность конвейера

Нестабильный CI-конвейер при запуске на одном и том же коде может давать разные результаты. Сегодня он «зелёный», завтра на тех же исходниках — «красный», а потом опять «зелёный».

Типичные причины:

- Нестабильные тесты: то проходят, то падают из-за таймингов или случайных данных.
- Зависимость от внешних ресурсов, которые могут быть временно недоступны (например, HTTP API).
- Параллельные процессы мешают друг другу, так как используют общие файлы, базы или сети.
- Environment слишком «грязный» и иногда содержит остатки от других задач.
- Случайное обновление зависимостей при сборке без lock-файла.

Почему это плохо:

- **Подрывает доверие к CI.** Если конвейер то падает, то проходит без изменений в коде, команда перестаёт доверять CI. Возникает культура игнорирования ошибок.
- **Заставляет тратить время на повторные запуски.** Разработчики начинают вручную несколько раз запускать конвейер, надеясь на «удачный проход».
- **Может скрыть реальные ошибки.** Если нестабильный тест то падает, то проходит, команда быстро перестаёт воспринимать его всерьёз. На этом фоне легко пропустить момент, когда он сломается уже по реальной причине.

### Как это исправить

1. Стабилизировать тесты:

- убрать рандомизацию, или фиксировать seed;
- добавить моки (заглушки) для нестабильных внешних сервисов;
- увеличить таймауты в тестах, если ошибки вызваны слишком короткими ожиданиями.

2. Изолировать окружения.

Каждая тестовая задача должна запускаться в чистом изолированном контейнере. Не делите базу данных между параллельными тестами.

3. Фиксировать зависимости.

Используйте lock-файлы (`package-lock.json`, `yarn.lock`, `pom.xml` c зафиксированными версиями). Это защитит от внезапного обновления пакетов.

4. Использовать `retry` там, где уместно.

Для тестов, которые могут фейлиться по временным причинам (например, HTTP-запрос к внешнему API), есть смысл настроить `retry`:

```YAML
integration_tests:
  script: npm run integration
  retry: 2 
```

**Важно**: `retry` — это временная страховка, а не полноценное решение проблемы. Если тест нестабилен постоянно, его нужно исправлять, а не бесконечно перезапускать.

5. Добавить health-check для внешних сервисов.

Если тесты зависят от сторонних API, перед запуском стоит проверить их доступность и завершить выполнение с понятным сообщением, если сервис недоступен.

### Вывод

CI-конвейер должен на одних и тех же исходниках всегда давать один и тот же результат. Если тесты нестабильны, это баг, требующий исправления, а не «маленькая неприятность».

Нестабильный CI медленно разрушает культуру качества. Сначала люди начинают игнорировать падающие конвейеры, потом перестают доверять CI, а в итоге пропускают настоящие ошибки.

## Практическое задание 2

Представим, что вы унаследовали `.gitlab-ci.yml`, написанный новичком. Он запихнул всё (линтер, тесты и сборку) в одну задачу. Конвейер работает, но очень медленно. Он не показывает прогресс, а если упал линтер — приходится перезапускать всё с нуля.

Ваша задача — применить lean-принципы и исправить антипаттерн «монолитная задача».

Подумайте, как разделить этот job на отдельные шаги так, чтобы:

- ошибка находилась раньше,
- результат был понятнее в интерфейсе CI,
- зависимости не устанавливались повторно без необходимости.

```YAML
stages:
  - build

ci_all_in_one:
  stage: build
  script:
    - pip install -r requirements.txt
    - flake8 src/
    - pytest tests/
    - pip install -r requirements.txt --target=dist/ 
```
![[Pasted image 20260805164725.png]]

### Пример решения

```YAML
stages:
  - lint
  - test
  - build

default:
  before_script:
    - pip install -r requirements.txt
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths:
      - ~/.cache/pip

lint_job:
  stage: lint
  script:
    - flake8 src/

test_job:
  stage: test
  script:
    - pytest tests/ --maxfail=1 --disable-warnings -q

build_job:
  stage: build
  needs:
    - lint_job
    - test_job
  script:
    - pip install -r requirements.txt --target=dist/
  artifacts:
    paths:
      - dist/ 
```

Чем этот вариант лучше исходного:

- Теперь GitLab показывает стадии `lint` → `test` → `build`. Видно, где что выполняется.
- Линтер и тесты запускаются одновременно, ускоряя обратную связь.
- Сокращается общее время пайплайна (нет повторных установок).
- Сборка (`build_job`) стартует, только если проверки пройдены успешно.
- Уменьшается трафик между GitLab Runner и PyPI.
- Конвейер становится ближе к lean — без потерь и дублирования.

## Мини-чек-лист хорошего CI-пайплайна

- Ошибки находятся рано
- `jobs` не дублируют друг друга
- Зависимости и результаты переиспользуются
- Обратная связь приходит быстро и понятно
- Один и тот же код даёт предсказуемый результат
