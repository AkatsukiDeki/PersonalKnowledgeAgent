**Intent:** FACTUAL | **Condensed Query:** Какую конкретно команду Git мы использовали для хотфикса в задаче с `nginx_logparser`? | **Sufficient Evidence:** True
**Ответ:**
> Для выполнения хотфикса и переноса исправления бага из ветки `bugfix/parse_status` в релизную ветку `release/1` мы использовали команду `git cherry-pick`. 

Конкретная команда, которую необходимо использовать для выполнения хотфикса, выглядит следующим образом:

```Bash
git cherry-pick 7672a25
```

Где `7672a25` — это хеш коммита с багфиксом.

### Q2: А почему нельзя было использовать `git merge` для этой же задачи?
**Intent:** FACTUAL | **Condensed Query:** Почему нельзя использовать git merge вместо git cherry-pick для переноса исправления бага из ветки bugfix/parse_status в релизную ветку release/1? | **Sufficient Evidence:** True
**Ответ:**
> Использование `git merge` в данном случае не было оптимальным решением по нескольким причинам:

1. **Линейная история коммитов**: Цель была точечно перенести коммит с исправлением бага из отладочной ветки `bugfix/parse_status` в релизную ветку `release/1`, сохранив историю линейной. Использование `git merge` создало бы дополнительный коммит слияния, что нарушило бы это требование.

2. **Одиночный коммит**: Требовалось перенести только один конкретный коммит (`7672a25`) без внесения изменений из других коммитов или добавления новых файлов. `git merge` обычно объединяет несколько коммитов, что не соответствует данной задаче.

3. **Изоляция изменения**: Перенос отдельного коммита с помощью `git cherry-pick` позволяет сохранить историю изменений более чистой и контролируемой, особенно в условиях активной разработки и множества веток. Это помогает избежать конфликтов и упрощает понимание истории проекта.

Таким образом, `git cherry-pick` оказался более подходящим инструментом для задачи переноса конкретного исправления без изменения структуры линейной истории коммитов.

### Q4: Что общего между принципом Lean в CALMS и нашими практиками в программировании?
**Intent:** ANALYTICAL | **Condensed Query:** Что общего между принципом Lean в CALMS и нашими практиками в программировании? | **Sufficient Evidence:** True
**Ответ:**
> Принцип Lean в модели CALMS имеет несколько важных особенностей, которые могут быть полезны для программистов:

1. **Умение признавать ошибки**: В контексте принципа Lean важно быстро выявлять и исправлять проблемы, чтобы избежать их накопления. Это напрямую влияет на скорость разработки и качество продукта.

2. **Системный подход к улучшению процессов**: Lean не только оценивает текущие процессы, но и постоянно ищет способы их оптимизации. Программисты могут применять этот принцип, регулярно рефакторя код, улучшая алгоритмы и облегчая поддержку.

3. **Автоматизация ручных процессов**: Хотя некоторые процессы могут казаться эффективными "и так", автоматизация даже этих может значительно сократить время разработки и уменьшить вероятность ошибок. Примером может служить автоматизация тестирования или сборки проекта.

4. **Получение быстрой обратной связи**: Принцип Lean подчеркивает важность того, чтобы изменения были внедрены как можно скорее и чтобы их результаты могли быть быстро оценены. В программировании это может означать частые интеграции кода, непрерывное тестирование и быстрое исправление обнаруженных багов.

5. **Минимизация избыточности**: Lean направлен на удаление излишних шагов в процессах. В программировании это может быть применено к оптимизации кода, уменьшению сложности алгоритмов и устранению дублирования.

Программисты могут интегрировать эти принципы в свои рабочие процессы, чтобы повысить эффективность, качество и скорость разработки.

### Ранние проекты:
1. **Чёткое разделение ролей**: Разработчики писали код, а операционные команды отвечали за его запуск и стабильную работу. Эти две группы находились в изоляции друг от друга.
2. **Постоянное напряжение**: Новые версии ломали существующие процессы, баги проявлялись в продакшене, и откат к предыдущим версиям был проблематичен.

### Текущие проекты (после перехода на DevOps):
1. **Изолярованные ветки**: Все изменения разрабатываются в изолированных ветках.
2. **Автоматизированное тестирование**: Изменения проходят автоматизированное тестирование перед выкаткой.
3. **Выкатка поэтапно через фиче-флаги**: Выкатка осуществляется поэтапно, что позволяет быстро откатываться в случае необходимости.
4. **Упрощённый GitFlow**:
   - **`main`**: Основная и стабильная ветка, содержащая готовый к развёртыванию код. Все новые функции и исправления попадают сюда через merge request.
   - **`release/X`**: Ветки для подготовки релизов, где проводятся финальные тесты и исправляются последние баги перед выпуском новой версии.
   - **Исправления в отдельных ветках (`bugfix` и `hotfix`)**: Все исправления вносятся в отдельных ветках, а не напрямую в `release`.
   - **`feature/название_фичи`**: Ветки для разработки новых функциональных возможностей.
